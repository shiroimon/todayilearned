一言でいうと

Compose で並列化するとは、同じワーカーコンテナを複数立てて、仕事（ファイル）を分け合わせること。
ただし Compose がやってくれるのは「箱を増やす」まで。どの箱がどのファイルを処理するかはアプリ側の仕事。

役割分担

担当 受け持つこと 変えたいときに触るもの
compose.yml 構成（イメージ・環境変数・ボリューム・依存関係） YAML
docker compose CLI 何個立てるか、どの引数で立てるか コマンド
アプリ（main.py） 取得 → 変換 → 書き込みの中身、仕事の取り合い Python

Important

YAML を書いた時点ではまだ分散していない。 各サービスはデフォルトで 1 コンテナ。
増やすのは YAML の書き換えではなく CLI（--scale / run）。

構成例 

# compose.yml
services:
  worker:
    build: .
    env_file: .env          # 接続情報は YAML に直書きしない
    depends_on:
      - db

  db:
    image: postgres:16
    env_file: .env
    volumes:
      - db-data:/var/lib/postgresql/data

volumes:
  db-data:

Warning

Gemini の回答には version: '3.8' が付いていたが、Compose v2 では不要。書くと警告が出る。

$ docker compose version
Docker Compose version v2.40.3-desktop.1
$ docker compose config -q
level=warning msg="/tmp/cmp/compose.yml: the attribute `version` is obsolete, it will be ignored, please remove it to avoid potential confusion"

コマンドも docker-compose（v1, ハイフンあり）ではなく docker compose（v2, プラグイン）。

ワーカーの増やし方は 2 通り

(1) ファイルごとに run で 1 個ずつ立てる 

docker compose run --rm -e FILE_TO_PROCESS=file1.csv worker
docker compose run --rm -e FILE_TO_PROCESS=file2.csv worker
docker compose run --rm -e FILE_TO_PROCESS=file3.csv worker
  • 処理対象を 起動時に環境変数で渡す。処理が終わればコンテナは消える（--rm）
  • 割り振りを人間（かシェルスクリプト）がやるので、アプリは単純なまま
  • ファイルが多いと手で叩いていられない → xargs -P などで並べることになる

(2) up --scale で同じワーカーを N 個立てる 

docker compose up -d --scale worker=3
  • 同じ設定のコンテナが 3 個立つ。3 個とも同じ環境変数を持つので、放っておくと同じファイルを 3 回処理する
  • だから「次に処理するファイル」を取り合う仕組み（キュー）がアプリ側に要る
flowchart LR
  Q[(キュー<br>file1..fileN)] --> W1[worker_1]
  Q --> W2[worker_2]
  Q --> W3[worker_3]
  W1 --> DB[(PostgreSQL)]
  W2 --> DB
  W3 --> DB

キューの実体は Redis / SQS / Pub/Sub、DB のテーブルに SELECT ... FOR UPDATE SKIP LOCKED で取り合わせる、など。

Caution

--scale を使うサービスに container_name や固定のホスト側 ports を書くと、名前・ポートが衝突して 2 個目以降が立たない。

どこまで Compose で引っ張るか

段階 手段 限界
1 台・ファイル数少 run を並べる 割り振りが手作業
1 台・ファイル数多 --scale ＋ キュー 1 台の CPU / メモリが天井
複数台 Swarm / Kubernetes Compose 単体の守備範囲外

Gemini は「複数の compose ファイルを別々のサーバーで動かす」も分散の手段に挙げていたが、それはマシンを分けて手で配っているだけで Compose の機能ではない。
複数台にまたがって数を管理したいなら Kubernetes の replicas の話になる（cf. Kubernetes Catchup）。

1 台の中での並列（プロセス / スレッド / async の使い分け）は Fundamentals & System Design Roadmap に書いた。
コンテナを増やすのは「プロセスを増やす」の延長で、DB 側の同時接続数が次のボトルネックになりやすい。

回答のコード例で直したいところ

  • 1 行ずつ INSERT している（df.iterrows() ＋ cursor.execute）。ワーカーを増やす前にここが遅い。executemany / COPY / df.to_sql(..., method="multi") でまとめて書く
  • パスワードを YAML に直書きしている。.env か secrets に逃がす
  • 冪等でない。同じファイルを 2 回処理すると行が二重に入る。キューで取り合う設計なら、リトライで同じファイルが再配送される前提で、ON CONFLICT などで上書きにしておく

Note

--scale の実際の挙動（コンテナ名の付き方・ログの混ざり方）はまだ手元で試していない。

振り返り : 実際は Compose、今なら STS

ここまでは Compose の一般論。実際に相談したかったのは 他社の S3 にある大量の Parquet を自社の BigQuery に移す 話だった。
実際の移行は Docker Compose でワーカーを増やしてやった。 Storage Transfer Service（STS）の存在は後から知った。

条件 値
移行の頻度 1 回きり
対象 全量
egress（転送料金） 相手持ち
認証方式 不明
S3 のリージョン US

今ならこうする : STS → GCS → bq load 

flowchart LR
  S3[(他社 S3<br>Parquet)] -- Storage Transfer Service --> GCS[(自社 GCS<br>生ファイル退避)]
  GCS -- bq load --> BQ[(自社 BigQuery)]
  • 1 回きり・全量 なので、差分同期も「移さずに読む」（BigQuery Omni / BigLake）も要らない。丸ごとコピーが一番単純
  • egress が相手持ち なので、S3 に取りに行くのは 1 回で済ませたい
    • GCS に生ファイルを置いておけば、ロードや型の失敗はこちら側だけでやり直せる
    • STS は途中再開でき、再実行しても転送済みのファイルは飛ばす
  • GCS → BigQuery のロードジョブは無料。Python で 1 行ずつ書き込むより安くて速い

Compose でワーカーを増やすやり方は、STS とロードジョブがやってくれることを手で作り直していたことになる。
しかも途中で失敗すると、S3 へ取りに行き直す（= 相手の egress が増える）作りになりやすい。
移しながらマスキングなどの加工が要る場合でも、いったん GCS に落としてから自社側で加工するほうが安全。

認証は IAM ロールで頼む

  • アクセスキーを発行してもらう代わりに、STS のサービスアカウントが AWS の IAM ロールを借りる方式にする（STS の federated identity 認証）
  • 長く使えるキーを社外に渡さずに済むので、相手のセキュリティ審査を通しやすい
  • 相手に頼むこと
    • ロールを作り、Google 側からの引き受け（AssumeRole）を許可する
    • そのロールに s3:GetObject / s3:ListBucket だけを付ける
    • アカウントをまたぐのでバケットポリシー側の許可も要る（cf. IAM Miscellaneous）
    • 移行が終わったらロールを消す

段取り

  1. 相手から aws s3 ls --recursive --summarize の結果（ファイル数・合計サイズ）とフォルダ構成をもらう
  2. GCS バケットを BigQuery のデータセットと同じロケーション に作る（同じ場所でないとロードできない）
  3. STS で S3 → GCS。転送ログで失敗 0 件を確認する
  4. 数ファイルだけ試しにロードして、型のズレを見る（INT96 のタイムスタンプ、LIST 型、桁の大きい DECIMAL）
  5. フォルダ単位で bq load --source_format=PARQUET。パーティションもここで決める
  6. 突き合わせ : ファイル数（S3 = GCS）、行数（Parquet のフッターに書かれた行数の合計 = BigQuery）
  7. 後片付け : GCS のコピーは少し置いてから消すか安いストレージクラスへ移す。相手にはロールの削除を依頼する

Note

未確定 : 自社 BigQuery のロケーション（2 の置き場所が決まる）、移行時の加工の要否。
