pre_operations / post_operations

テーブルを作る SQL の前後に別の SQL を挟み込むブロック。SQLX ファイルの config ブロックの外に書く。

ブロック 走るタイミング 公式に載っている用例
pre_operations テーブル作成の 前 CREATE TEMP FUNCTION の定義
post_operations テーブル作成の 後 GRANT ... ON TABLE ${self()} TO ... 
config { type: "table" }

pre_operations {
  CREATE TEMP FUNCTION AddFourAndDivide(x INT64, y INT64)
    RETURNS FLOAT64
    AS ((x + 4) / y);
}

SELECT AddFourAndDivide(a, b) AS v FROM ${ref("source_table")}

post_operations {
  GRANT `roles/bigquery.dataViewer`
  ON TABLE ${self()}
  TO "group:allusers@example.com"
}

押さえておくところ。

  • 複数文を書くときは --- で区切る
  • ${self()} は「このアクションが作るテーブル」への参照。resolve(name()) と同値なので、schema / name を後から変えても追随する
  • JavaScript API 側では .preOps(ctx => ...) / .postOps(ctx => ...)
  • 「テーブル作成の前後」であって「クエリの前後」ではない。BigQuery コンソールに本体クエリだけコピペして流しても pre/post は走らない。Dataform UI でも実行の入口によって含まれ方が変わるので、pre_operations に DECLARE を書いた状態でプレビューすると Unrecognized name: が出る

incremental は「積み上げ」しかしない

type: "incremental" が出す DML は、uniqueKey の有無で変わる。

  • uniqueKey なし … INSERT。新しい行を足すだけ
  • uniqueKey あり … MERGE。同じキーの行は更新される（updatePartitionFilter が効くのはこちらだけ）

そして ${when(incremental(), ...)} で「2 回目以降だけ効く WHERE」を書く、というのが定石。

config { type: "incremental" }

SELECT timestamp, message FROM ${ref("productiondb", "logs")}
${when(incremental(), `WHERE timestamp > (SELECT MAX(timestamp) FROM ${self()})`)}

ここで効いてくるのが、uniqueKey が無いと同じ範囲を 2 回流した時に素直に重複するという点。 上の例は MAX(timestamp) で自分の到達点を見ているので普通は重ならないが、 「対象日を指定して流し直す」運用に切り替えた途端に破綻する。

DELETE INSERT を pre_operations で組む

Dataform には dbt の delete+insert / insert_overwrite に当たる incremental strategy の指定が無い。 なので pre_operations で先に消してから入れるのを自分で書く。

config {
  type: "incremental",
  schema: "sample_dataset",
  name: "sink_table",
}

pre_operations {
  DELETE FROM ${self()} WHERE date = '2024-05-13'
}

WITH source_table AS (
  SELECT DATE('2024-05-13') AS date, 1 AS user_id, 100 AS value
  UNION ALL
  SELECT DATE('2024-05-13') AS date, 2 AS user_id, 200 AS value
)

SELECT * FROM source_table WHERE date = '2024-05-13'

uniqueKey の MERGE と何が違うのかというと、source から消えた行に追随できるか。 MERGE は matched なら UPDATE / not matched なら INSERT しかしないので、 source 側で削除された行は sink に残り続ける。 対象範囲ごと DELETE してから入れ直すこの形なら、その行も消える。

書き方 出る DML source から消えた行 同じ範囲を再実行
incremental のみ INSERT 残る 重複する
incremental ＋ uniqueKey MERGE 残る 上書きされる
incremental ＋ pre_operations の DELETE DELETE → INSERT 消える 入れ直される
--full-refresh CREATE OR REPLACE 消える 全部作り直し

落とし穴 1 — と思っていたが、初回は勝手に避けてくれる

最初に引っかかったのがここ。pre_operations はテーブル作成の前に走る。 ということは 初回はまだテーブルが存在しないわけで、素の DELETE FROM ${self()} は その一回目で落ちるんじゃないのか。--full-refresh も同じ心配がある。

BigQuery を叩く前に dataform compile --json で生成物を覗いたら、心配は要らなかった。

$ dataform compile --json | jq '.tables[] | {name: .target.name, preOps, incrementalPreOps}'
定義 preOps incrementalPreOps
type: "table" ＋ pre_operations 入る —
type: "incremental" ＋ pre_operations 無い 入る
type: "incremental" ＋ pre_operations {} 無い [""]（空文字列）

incremental テーブルは「初回 / full refresh で使う非増分クエリ」と「増分クエリ」の 2 系統を持っていて、 pre_operations は後者にしか付かない。だから初回も --full-refresh も、 DELETE は流れずに CREATE OR REPLACE だけが走る。Dataform が勝手に振り分けている。

つまり when(incremental(), ...) で囲む必要が無い。 囲んでも incrementalPreOps の中では incremental() が常に true なので結果は変わらない。

落とし穴 2 — 空の pre_operations だけは残っている

上の表の 3 行目。pre_operations {} と空で書いた場合だけ、incrementalPreOps に 空文字列の要素が 1 つ残る。これが ; SELECT ... という不正な SQL になる、という既知の不具合。

  • #942（2020-08 起票 / closed）… type: "table" での同じ現象
  • #1569（2023-11 起票 → 2024-04-04 closed）… incremental でのみ再現する版。メンテナが「内部で直せるので修正を出す」とコメントして閉じている

Warning

closed になっているが、core 2.7.0 の compile 結果には [""] がまだ残っていた。 空文字列が実行時にどう組まれるかまでは compile では見えないので、 実害があるかは別途 --dry-run で確かめる必要がある。

踏みにいく状況は限られる。when() の falseCase を省略しても incremental 側には true 分岐が入るので空にならない。 条件を反転させて ${when(!incremental(), ...)} と書いたときが該当する。 その場合は第 3 引数にダミーの有効文を置いて逃げる。

pre_operations {
  ${when(incremental(),
    `DELETE FROM ${self()} WHERE date = '2024-05-13'`,
    `SELECT 'noop'`)}
}

なお config { type: "operations" } のコンテキストには incremental() が存在しないので、 when(incremental(), ...) は使えない。分岐させたい処理は incremental テーブル側の pre_operations に寄せることになる。

落とし穴 3 — 対象日のハードコード

上の例は '2024-05-13' を直書きしている。当然これでは毎日動かない。動的にする道具は 3 つ。

  1. includes/ の定数 … includes/constants.js に置いて ${constants.start_date} で参照する。 updatePartitionFilter で遡及範囲を書くときにも同じ形を使う
  2. コンパイル変数 … workflow_settings.yaml（core 2.x なら dataform.json）の vars に定義して、CLI なら --vars=key=value、 Dataform UI ならリリース構成の compilation variables で上書きする。特定日だけ流し直すバックフィルはこれ
  3. BigQuery 側で相対指定 … WHERE date >= DATE_SUB(CURRENT_DATE(), INTERVAL 3 DAY)

日次で回すだけなら 3 が一番堅い。「直近 N 日を毎回消して入れ直す」形にしておくと、 遅れて届いたデータを勝手に拾い直してくれる。範囲を絞りたいときだけ 2 を足す。

core 2.7.0 の dataform compile --json と --help の実出力で確認したもの。

config に書けるプロパティは、間違えると全部教えてくれる

存在しないキーを書くとコンパイルが落ちるのだが、そのエラーがサポートされているプロパティを全部列挙する。 リファレンスを開くより速い。

$ dataform compile
Error: Unexpected property "labels" in table config. Supported properties are:
["type","disabled","protected","name","redshift","bigquery","snowflake","sqldatawarehouse",
 "presto","tags","uniqueKey","dependencies","hermetic","schema","assertions","database",
 "columns","description","materialized"]

この一覧に labels が無いのがポイントで、BigQuery ラベルは bigquery の下に入れる。 partitionBy / clusterBy / updatePartitionFilter と同じ階層。

config {
  type: "incremental",
  bigquery: { labels: { team: "de", env: "dev" } }
}

事故から守る — protected / disabled

キー 何が起きる
protected: true incremental 専用。full refresh 指定を無視して増分のまま完走する
disabled: true 実行されなくなるが、他のアクションは依存し続けられる

protected は「消したら二度と作れない」テーブル向け。日次スナップショットのように、 ソースが後に残らない形で積み上げているものは、誤って full refresh されると復旧できない。 エラーにはならず、full refresh の指定が黙って無視される。

Caution

--full-refresh と --schema-suffix を併用すると、protected なモデルでエラーになるという報告があった （#1892、2025-01 起票 → 2025-06 closed）。 UI からの full refresh では出ない、という差がある。

disabled は「止めたいが依存グラフからは外したくない」ときに使う。 コメントアウトすると下流が ref() の解決に失敗するが、disabled なら参照は生きたまま実行だけ止まる。 dataform compile の一覧にも [disabled] と出る。

BigQuery を叩く前に見る — compile --json / --dry-run

この記事の「落とし穴 1」は、これで自分の思い込みが崩れた。

コマンド 何が起きる
compile 依存グラフを解決するだけ。BigQuery に接続しない
compile --json 解決後の全アクションを JSON で吐く。生成 SQL まで見える
compile --watch ファイルの変更を監視して自動で再コンパイル
run --dry-run 実行せず、組み立てた SQL をコンソールに出す

compile は BigQuery に繋がないので、認証が通っていない状態でも構文と依存は確認できる。 pre_operations を書いたら、--json で preOps / incrementalPreOps のどちらに入ったかを見るのが確実。

開発用データセットに逃がす — --schema-suffix 

$ dataform run --schema-suffix=dev

出力先のデータセット名すべてに suffix が付く（reporting → reporting_dev）。 本番のテーブルを踏まずに一通り流せる。compile 側にも同じフラグがあるので、 「どこに書き込もうとしているか」を実行前に確認できる。

品質を見る — assertions

config に書く組み込み assertion は 4 種類。だが生成されるアクションの数は 4 つではない。

config {
  type: "table",
  assertions: {
    nonNull: ["a"],
    uniqueKey: ["a"],
    rowConditions: ["a > 0"]
  }
}
SELECT 1 AS a, 2 AS b

これをコンパイルすると、assertion は 2 つしか出ない。

$ dataform compile
2 assertion(s):
  dataform_assertions.dataform_probe_assert_assertions_uniqueKey_0
  dataform_assertions.dataform_probe_assert_assertions_rowConditions

nonNull は独立した assertion にならず、rowConditions 側に畳み込まれる。 生成されたクエリを見ると IS NOT NULL の条件として UNION ALL で合流していた。

SELECT 'a > 0'         AS failing_row_condition, * FROM `...probe_assert` WHERE NOT (a > 0)
UNION ALL
SELECT 'a IS NOT NULL' AS failing_row_condition, * FROM `...probe_assert` WHERE NOT (a IS NOT NULL)

failing_row_condition 列にどの条件で落ちたかが入るので、失敗時はこれを見れば原因が分かる。 uniqueKey のほうは独立したアクションになり、GROUP BY して COUNT(1) > 1 を拾う形。

出力先は dataform_assertions データセット（assertionSchema で変えられる）。 rowConditions は任意の SQL 式が書けるので、実質ここに何でも詰められる。

Dataform の外で作られたテーブルを検査したい場合は、別ファイルの手動 assertion を書く。 1 行でも返したら失敗、という約束。

config { type: "assertion" }

SELECT * FROM ${ref("model")} WHERE output IS NULL

単体テスト — type: "test"

assertion が「本番データを検査する」のに対して、こちらは「ロジックを固定の入力で検査する」。 input で ref() の中身を差し替える。

config { type: "test", dataset: "model" }

input "src" {
  SELECT 1 AS input UNION ALL SELECT 2 AS input
}

SELECT 2 AS output

compile --json で見ると、ref("src") が input の中身にサブクエリとして置換されていた。

{
  "name": "model_test",
  "testQuery": "SELECT MAX(input) AS output FROM (SELECT 1 AS input UNION ALL SELECT 2 AS input)",
  "expectedOutputQuery": "SELECT 2 AS output"
}

押さえておくところ。

  • test は tables でも assertions でもなく tests という別枠に入る。 Compiled N action(s) の N にも数えられないので、書いたのに一覧に出なくても壊れてはいない
  • 実行は dataform test。dataform run --run-tests を使うと、テストが通らない限り run しない
  • SQLX 1 ファイルにつきテストは 1 つ。複数パターンを並べたければ JavaScript 側でまとめる

ref() と resolve() の違い

どちらも「テーブルへの有効な SQL 参照」を返すが、ref() は依存関係を作り、resolve() は作らない。 実行順序を保証したいなら ref()。循環依存を切りたいなど、参照はしたいが順序は自分で握りたい場面だけ resolve()。 ${self()} は resolve(name()) と同値なので、自分自身への依存は作られない。

残りの config キー

キー 何が起きる
materialized: true type: "view" のときだけ有効。BQ のマテリアライズドビューになる
hermetic: true 依存を全部宣言したという申告。false は宣言外のソースに依存
bigquery.labels BigQuery ラベル。コスト配賦やジョブの絞り込みに効く

hermetic はコンパイル結果では hermeticity: "HERMETIC" という enum になる。 宣言していないテーブルを直接 SQL に書いている場合は false にしておくと、意図が残る。

実行を BigQuery 側から追う — --job-prefix 

$ dataform run --job-prefix=nightly

BigQuery のジョブ ID が dataform-nightly-... になる。 INFORMATION_SCHEMA.JOBS を引けば、どの実行がどれだけスキャンしたかを後から集計できる。 BigQuery 以外のウェアハウスでは効果が無い。

dataform format

SQLX のフォーマッタ。dataform format でプロジェクト内のファイルを整形する。 オプションは無く、--help にも --track しか出てこない。

CLI フラグ早見表

フラグ 何が起きる
run --dry-run BigQuery を叩かず、生成された SQL をコンソールに出す
run --schema-suffix=dev 出力先データセットを xxx_dev に逃がす
run --run-tests 単体テストが通らなければ run しない
run --full-refresh incremental をゼロから作り直す。protected には効かない
run --actions / --tags 実行対象を名前 / タグで絞る。--actions は * が使える
run --include-deps 選んだアクションの上流も一緒に実行する
run --include-dependents 選んだアクションの下流も一緒に実行する。巻き込み事故の元
run --vars=k=v コンパイル変数を注入する
run --job-prefix BQ のジョブ ID に prefix を足す
compile --json 解決済みのグラフを JSON で吐く
compile --watch 変更を監視して自動で再コンパイル
dataform format SQLX を整形する

--include-dependents は下流を全部引き連れていくので、1 つ直したつもりが データマート全体を作り直していた、という事故が起きうる。 --dry-run で対象を確かめてから外すのが安全。
