Why

SSIA

コードを書く速度が上がった結果、ボトルネックがレビューに移った。。

そして、レビューにも AI を入れると今度は別の違和感が出てくる。
「AI が書いたコードを AI がレビューして、人間は Approve を押すだけ」– これは何をしていることになるのか?!

「レビューを AI に任せるか / 任せないか」の二択で考えるから詰まる。
レビューは単一の作業ではないので、段階に分解すれば線が引ける! そんな光明な記事があったので、実運用に落とした話をまとめる。

What

0. レビューを6段階に分解

# 段階 見るもの AI 人間 主な担い手
1 Format インデント、改行、クォート 100% 0% Prettier / pre-commit hook
2 Lint 未使用変数、危険な構文 100% 0% ESLint / Ruff
3 Style 命名、可読性、慣習との一致 90% 10% CodeRabbit / Copilot
4 Logic 境界値、例外系、仕様との一致 60% 40% Claude Code Review
5 Design 責務分割、拡張性、依存の向き 30% 70% ペアレビュー
6 Architecture システム全体の整合、技術選定 0% 100% シニア / テックリード

上に行くほど 「正解が決まっている」 ので機械が強い。 下に行くほど 「文脈と将来の予測」 が必要になるので人間が要る。

Tip

一番効くのは 1〜3 を人間のレビューから完全に追い出すこと。 ここに時間を使っていると、4〜6 に回す集中力が残らない。 「インデントを指摘するレビュー」が残っているチームは、まず CI に落とす。

逆に注意すべきは 6。 AI は「このコードは正しいか」には答えられるが、「このコードが存在すべきか」には答えられない。 アーキテクチャの判断は、組織の事情・採用計画・3年後の運用まで含んだ意思決定なので、 そもそも diff の中に判断材料が無い。

1. 「コードを読まないでどう責任を持つのか」

段階分けをすると、必ずこの疑問に行き着く。 自分が1行ずつ読んでいないコードに、どうやって責任を持つのか🤔

責任の根拠を「読解」から「検証と説明」へ移す（QA担当サーセン）

「全部読んだ」は、実は昔から責任の根拠として弱かった。 1000行の diff を目視して見落とさない人間はいない。

読んだかどうかではなく、そのコードが正しいと言える根拠を持っているかに置き換える。

  • 仕様を満たすことを示すテストがあり、それが落ちる状態を一度見た
  • 境界値・異常系について「どう振る舞うか」を説明できる
  • 変更が影響する範囲を把握していて、影響外だと言える理由がある

これらはコードを1行ずつ読まなくても成立する。逆に、 全部読んだが上の3つが言えないなら、それは責任を持てていない。

AI に「大丈夫です」と言わせない

一番危険なのは、AI レビューの結論 だけを受け取ること。 LGTM や「問題ありません」は、検証していないことと区別がつかない。

必ず 証跡を出させる 形で頼む。

# ❌ 結論だけ求める
> このPRをレビューして

# ⭕️ 根拠を要求する
> このPRをレビューして。指摘には必ず
>   (1) 該当ファイル:行番号
>   (2) その入力・状態だと何が壊れるかの具体的なシナリオ
>   (3) blocker / nit のどちらか
> を付けること。再現シナリオを書けない指摘は出さないでよい。

「具体的な失敗シナリオを書け」という制約は、もっともらしいが誤りな指摘（plausible-but-wrong）を落とすのに効く。 書けないということは、その指摘は成立していない。

(3) を足しているのは、深刻度（直すべきか）と確度（本当に問題か）が別の軸だから。 後述の high 以上は確度の低い指摘まで拾ってくるが、それは「軽い指摘」という意味ではない。 分けて書かせないと、blocker が nit の山に埋まる。

価値の置き場所が変わる

コードを書く力そのものの希少性は下がった。 残る価値は、課題を分解し、検証可能な形に落とし、成果まで持っていく総合力の側にある。

レビューで言えば、「この実装は間違っている」を見つけることより、 「そもそもこの要件の切り方でいいのか」を問えることの方が代替されにくい。

2. 敵対的にレビューさせる

普通に「レビューして」と頼むと、AI は 気になった点を挙げるモードになる。 これは指摘の数は出るが、当たり外れの区別が付かない。

そこで、姿勢そのものを変える。

  1. コード側の暗黙の主張を反証する — diff が暗黙に主張していること（「この JOIN は重複しない」「この期間フィルタで漏れはない」）に対し、成り立たない入力・境界を能動的に探しにいく
  2. 自分の指摘を反証する — 一度挙げた指摘それぞれに「これは本当に問題か、反証してみろ」と別視点をぶつけ、壊れなかったものだけ残す

これを成立させる条件が2つある。

要件 中身
独立性 実装者の意図や「こう書きたかったはず」を切り離した懐疑者の目で見る。作者を忖度しない
役割づけ 「良い点を探す」のではなく「壊せるか試す」。懐疑者に徹する

実装者本人と同じセッションでレビューさせると 1 が崩れる。 書かせたセッションと、レビューさせるセッションは分ける。

3. 自前レビュースキルは畳んで /code-review に寄せた

一時期、レビュー用のスキルやコマンドを何本も自作していたが、ほとんどをアーカイブした。

理由は単純で、ビルトインのレビュー機能が育ち、自前のものは 「メンテしていない古いプロンプト」になっていたから。 使われないルールが残っていると、生きているルールの相対的な重みが下がる（CLAUDE.md と同じ話）。

「どこまで探すか」がプロンプトから引数に移った 

/code-review [low|medium|high|xhigh|max|ultra] [--fix] [--comment] [<pr#>|<branch>|<path>]
引数 効くところ
low / medium 確度の高い指摘を少数だけ。日常の差分はこれで足りる
high 〜 max 網を広げる。不確実な指摘が混ざる前提で受け取る
ultra クラウドでの多エージェントレビュー（claude.ai のアカウントが要る）
--comment 指摘を PR のインラインコメントとして投稿
--fix レビュー後、指摘を作業ツリーに適用
<pr#> / <branch> / <path> 対象の指定。無指定なら現在の diff

自作スキルが勝てなくなったのはここ。
自然文で「重めに見て」「軽くでいい」と伝えている限り、同じ言葉が毎回同じ深さにならない。 段階が引数になっていれば、少なくとも再現する。

Note

レベルを省略すると 前回打ったレベルを再利用する。 「low のつもりが max が走る」が起きるので、効きを比べたい時は毎回明示する。

Warning

--fix は作業ツリーに直接当たる。コミット済みの状態から打つこと。 レビューの指摘と自分の未コミット編集が混ざると、どちらが誰の変更か diff から読めなくなる。

それでも残したもの

今残しているのは、ビルトインで代替できないものだけ。

使うもの 位置づけ
/code-review 通常の diff レビュー。デフォルトはこれ
/security-review 現ブランチの未マージ変更に対する脆弱性観点の専用パス
自作の敵対的レビュー 「反証させる」姿勢は汎用レビューと目的が違うので残す

/code-review が探すのは バグと、再利用・簡素化・効率の改善余地。 これは前節で言った「気になった点を挙げるモード」の、よく出来た版ではある。 だが 「この diff が暗黙に主張していることを壊しにいく」向きではないので、敵対的レビューは別枠のまま置いている。

Warning

自作スキルを増やす前に、ビルトインで足りないことを一度確認する。 「自分のプロンプトの方が良い」は、大抵1〜2ヶ月で逆転する。

4. 昔書いたチェックリストは、どこへ行ったか

以前、チーム用のレビューガイドを書いたことがある。 観点をカテゴリ別に並べて全部チェックボックスにした、よくある形のやつ。
今はまったく使っていないので、なぜ死んだのかを6段階に当て直してみた。

項目の行き先は4つに分かれた。

行き先 例 今の扱い
CI に落ちた フォーマット、未使用変数、マジックナンバー 人間のレビューには出てこない
AI が引き受けた 命名・可読性、重複コード、エッジケース、N+1、SQLi /code-review の担当範囲
人間に残った 責務分離、将来の拡張性、依存の向き、アーキとの整合 6段階の 5〜6。ここだけ読む
前提が反転した 「批判ではなく協働」「良いコードは褒める」 相手が AI なら要らない

死因は、この4つが同じチェックボックスで並んでいたことだった。

  • 平坦なリストは項目を等価に見せる。「マジックナンバー」と「将来の拡張性」が同じ1行になる
  • 上から順に埋めると、機械に落とせる項目で集中力が尽きる
  • どの項目もチェックが付く形なので、埋まったのに何も検証していない状態が成立する

要するにこのガイドは、この記事で言っている「1〜3 を人間から追い出す」の逆をやっていた。

反転したもの: 作法は人間相手の前提だった

ガイドには「避けるべきコメント例」も書いてあった。 「これは間違っている」「なぜこんな書き方をしたのか理解できない」「普通はこうしない」—— これらは 相手が人間だから避けるべきだった。書き手の心理的コストを下げる作法であって、指摘の正しさとは無関係。 AI レビュアーには忖度が要らないので、ここは丸ごと落ちる。むしろ逆（懐疑者に徹しろ）を要求する。

ただし 完全には消えない。--comment で AI の指摘を PR に投稿すると、 AI → 人間の経路に入った瞬間に作法が復活する。自動投稿の前に一度読んで、必要なら自分の言葉に直す。

生き残ったもの: AI が知り得ない観点と、接地の判断

まだ効いているのは2箇所だけだった。

  • プロジェクト固有の観点 — クエリのスキャン量（= 課金）、扱ってはいけないデータ、命名規約。この手のものは diff からは読めない。逆に汎用観点（命名・N+1・SQLi）を並べるのはビルトインと重複するだけで割に合わない。§3 の「ビルトインで代替できないものだけ残す」が、スキルではなく観点の側でも成立する
  • 「ローカルで確認すべきか」の基準 — 複数ファイルに跨る / 動かさないと分からない / 差分だけでは影響範囲が読めない。この基準は宛先が人間から AI に変わっただけでそのまま使える。<pr#> を渡して確実に見えるのは差分そのものなので、テストを走らせたい・周辺コードまで当たらせたいなら、ブランチを手元に落としてから打つ

5. レビューを受ける側の作法

境界を引いても、diff が読めない形なら 4〜6 段階目は誰にもレビューできない。

  • 差分を小さく保つ — 「AI が一気に書けるから」で1000行の PR を作らない。昔のガイドで分割提案の目安にしていたのは 400行で、AI に書かせると生成側は行数を気にしないので軽く超える
  • 意図を PR 本文に書く — なぜこの実装にしたか、何を捨てたかは diff に映らない
  • 機械的変更と設計変更を混ぜない — フォーマッタ一括適用とロジック変更を同じ PR に入れると、レビュー可能性がゼロになる
