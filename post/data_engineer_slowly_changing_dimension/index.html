TL;DR

SCD = Slowly Changing Dimension（ゆっくり変化するディメンション）。
ディメンションの属性値が時間とともに変わるとき、その変化をどう保存するかの分類で、Kimball が Type 0〜7 まで定義している。実務で出てくるのはほぼ Type 1 と Type 2 の 2 つ。

観点 Type 1（上書き） Type 2（行を足す）
やること 古い値を新しい値で潰す 古い行を閉じて、新しい行を追加する
持てる情報 今の値だけ 「いつからいつまでこの値だったか」
主キー ナチュラルキーのまま サロゲートキーが必要（1 実体に複数行が対応）
行数 実体の数と一致 実体の数 × 変更回数だけ増える
過去のレポートの再現 ❌ できない（数字が変わる） ⭕️ できる
実装コスト merge 1 パス、素直 有効期間の設計 + 閉じる / 足すの 2 アクション
向いているもの 誤記の訂正、表記ゆれの是正 業務上の意味が変わる属性（プラン・部署・区分）

判断の分かれ目は 1 つだけ。その変更は「訂正」か「事実の変化」か。
大阪 を 大坂 と打ち間違えていたのを直すのは訂正なので Type 1 でよい。ユーザーのプランが free から pro に変わったのは訂正ではなく事実の変化なので、潰すと過去が嘘になる。

古典的 DWH の語彙としての SCD

SCD は個別のテクニックというより、Kimball のディメンショナルモデリングという体系の中の一部品。

Note

Ralph Kimball（1944-）は Stanford で電気工学の博士号（1973）を取り、Xerox PARC で Xerox Star（マウス・アイコン・ウィンドウを載せた最初の商用製品）の主要設計者を務めたあと、1986 年に DWH 特化の RDB を作る Red Brick Systems を創業した人。
DWH の方法論は Kimball の bottom-up（ディメンショナルモデリング / バスアーキテクチャ）と Bill Inmon の top-down の 2 派に大別される。BigQuery / dbt まわりで「ファクトとディメンションに分ける」と言うとき、暗黙に指しているのは前者。

この体系の正典が『The Data Warehouse Toolkit』で、Type 0〜7 という分類そのものがここから来ている。

The Data Warehouse Toolkit: The Definitive Guide to Dimensional Modeling (3rd Edition) amazon.co.jp

SCD が載っているのは Chapter 5: Procurement（調達）。
「調達」という業務ドメインのケーススタディの中で、ディメンション属性の変化の扱いをまとめて論じる、という構成になっている。

前提の並びはこうなっている。

flowchart LR
    A["業務システム<br/>（OLTP・正規化）"] --> B["DWH<br/>（分析向けに非正規化）"]
    B --> C["ファクト表<br/>fact_order<br/>＝ 起きた出来事・数値"]
    B --> D["ディメンション表<br/>dim_user / dim_product<br/>＝ 出来事を説明する属性"]

  • ファクト表 … 起きた出来事とその数値（注文、決済、クリック）。行数が伸び続ける
  • ディメンション表 … その出来事を「誰が / 何を / どこで」と説明する属性。行数は多くない

ファクトは追記のみなので履歴の問題が起きない。
問題が起きるのは常にディメンション側で、「注文が起きた時点のユーザー属性」を後から引けるかどうかがここで決まる。「ゆっくり変わる」という言い方は、ファクトの発生速度に比べて属性の変化が遅い、という相対的な話をしている。

Kimball の Type 0〜7

Note

定義は Kimball Group の原文からの引用（拙訳）。公式は Type 7 まであり、「Type 6 まで」と書かれている資料は Type 7 が追加される前のもの。

Type 公式名 何をするか 実務頻度
0 Retain Original 値を一切変えない。「facts are always grouped by this original value」 低
1 Overwrite 上書きする。原文いわく「this technique destroys history」 高
2 Add New Row 行を足す。有効開始日 / 有効終了日 / 現在行フラグを持たせる 高
3 Add New Attribute 列を足して 1 世代前の値だけ残す。「used relatively infrequently」 低
4 Add Mini-Dimension 変化の速い属性群を別表（ミニディメンション）に切り出す 中
5 Add Mini-Dimension and Type 1 Outrigger Type 4 に「現在プロファイル」への Type 1 キーを埋め込む 低
6 Add Type 1 Attributes to Type 2 Dimension Type 2 の行に「現在値」の列も同居させ、当時の値 / 現在値の両方で切れるようにする 中
7 Dual Type 1 and Type 2 Dimensions ファクトにサロゲートキーと耐久キーの 2 本を持たせ、参照側で選ばせる 中

Type 3 は「1 世代前だけ残す」という中途半端さゆえに、Kimball 自身が使用頻度は低いと書いている。
Type 6 と 7 は「当時の値でも現在の値でも集計したい」という要求への回答で、中身は Type 2 の拡張。まず Type 2 を作れるようになってから考えればよい。

2013 年の本が、2026 年でもまだ効くのか

Kimball の体系は 1996 年（初版）に始まり、いま参照している第3版が 2013 年。無比類ではないが、置き換えられてもいないというのが実態で、層ごとに勝者が違う。

層 実質的な勝者 理由
生データ / 取り込み Medallion の bronze モデリングの話ではない
統合コア Data Vault 2.0 が侵食 ソース変更・監査証跡。金融/医療/公共
マート / 消費 Kimball 一強 BI ツールがこれ前提で作られている
サービング OBT / ワイドテーブル join を消す最適化。モデルではない
セマンティック層 Kimball の論理だけ残る 物理 star は不要、entity は必須

削られた（1） OBT が物理層を取った

Fivetran が 2022 年に TPC-DS 100 で取ったベンチマークでは、star schema を 1 枚の非正規化テーブル（OBT / One Big Table）に畳んだほうが、3 つの DWH すべてで速くなった。

DWH 改善幅
Redshift 約 25〜30%
Snowflake 約 25%（単純なクエリでは拮抗）
BigQuery 約 49%

カラムナ + 圧縮で「非正規化はストレージが高い」という前提が消えたのが背景にある。ただし 2 点。

  • これは 2022 年の数字。 近年は「モダンなカラムナエンジンは star の join も十分速く、差は縮んでいる」という揺り戻しがある（BigQuery の数値にはクエリコンパイル時間も含まれている）
  • 速いのは「正しいクエリ」だけ。 OBT は fan trap（粒度の違う表を畳んだことによる重複計上）で間違った結果を高速に返せる。ベンチマークは正しさを測っていない

そして OBT への批判は速度ではなく保守性に集中する。属性を 1 つ変えるとテーブル全体を書き直す、顧客の定義が全ワイドテーブルにコピーされて食い違う、そして 履歴が行に溶け込むので SCD が組めない。

削られた（2） Data Vault 2.0 が統合コアを取った

ソース変更が頻繁・監査証跡が必須・複数チームが並列ロードする環境（金融 / 医療 / 公共）では明確に勝っている。
ブレーキになっているのは技術ではなく人で、BARC / Eckerson Group の調査（2023年4月, n=92）では 採用企業の 48% が「スキルと研修の要件」を主な欠点に挙げている。次いで実装の複雑さ 35%、クエリ性能 32%。

削られた（3） Medallion が語彙を薄めた

bronze / silver / gold はレイヤ規約であってモデリング手法ではないのに、採用すると「モデリングの話をした気になる」。dbt の staging → intermediate → marts も同じで、marts の中身が Kimball かどうかは誰も強制していない。

それでも残っている理由

BI ツールが star schema を前提に作られている。 Tableau / Power BI / Looker はファクトとディメンションの関係を自動検出する前提で設計されており、ここは代替がない。

面白いのはセマンティックレイヤで、dbt Labs は公式に「Semantic Layer はモデリング非依存で、snowflake schema / star schema / data vault / その他の正規化テーブルのどれでも動く」と明言している。物理的な star を要求していない。

ところが MetricFlow は「全 semantic model に primary entity が必要」「entity を primary / foreign / unique / natural で型付けする」と要求する。これは star schema の関係そのもので、実在しない列に対してすら「仮想 primary entity」を割り当てさせられる。

Important

物理の星は消えたが、論理の星は残った。
Kimball の正当化の理由が入れ替わった、というのが一番正確な言い方になる。

  • パフォーマンス最適化 … OBT に負けた（ただし差は縮小中）
  • ガバナンス・柔軟性・履歴追跡の規律 … ここは今も代替がない

そして SCD はまさにこの「残った側」の中心にある。OBT では組めず、Data Vault では satellite が同じ仕事を担い、セマンティックレイヤは履歴を持ってくれない。
以降で扱う Type 2 は、Kimball が削られなかった部分そのもの。

Type 1 — 上書き

今の値だけ持つ。素直で、行数が増えない。

user_id plan department
U001 pro 営業

plan が free → pro に変わったら、この行の plan を pro に書き換えて終わり。

何が失われるかは明確で、free だった期間が消える。
Kimball が警告しているのはこの先で、すでに作った集計表・OLAP キューブも作り直さないと整合しなくなる。「先月出したレポートの数字が今日再実行したら違う」という事故は、ほぼこれが原因。

Type 2 — 行を足す

古い行を「閉じて」、新しい行を「足す」。Kimball が Type 2 に要求する追加列は 3 つ。

  1. Row effective date（有効開始）
  2. Row expiration date（有効終了）
  3. Current row indicator（現在行フラグ）
user_sk user_id plan valid_from valid_to is_current
1001 U001 free 2026-01-01 00:00:00 2026-06-01 00:00:00 false
1002 U001 pro 2026-06-01 00:00:00 null true

押さえるべき設計判断が 3 つある。

(1) サロゲートキーが必須になる

user_id（ナチュラルキー）はもう主キーになれない。1 人のユーザーに複数行が対応するため。
だから行ごとに一意な user_sk（サロゲートキー / 代理キー）を振り、ファクト表からはこの user_sk を参照する。

これが効くのは、ファクト表が発生時点のディメンション行を指したまま固定されること。あとからユーザーのプランが変わっても、過去の注文行が指す user_sk は動かないので、当時のプランで集計できる。

Tip

Kimball 用語では、変わらないほうの user_id を durable supernatural key（耐久キー） と呼ぶ。Type 7 はこの 2 本をファクトに両方持たせる方式。

(2) 有効期間は半開区間 [valid_from, valid_to) にする

境界の扱いは、閉区間（valid_to を「最後に有効だった瞬間」にする）より半開区間（valid_to を「次の行が始まる瞬間」にする）が安全。

  • 閉区間だと valid_to = 次の行の開始 - 1秒 のような書き方になり、粒度（秒 / ミリ秒 / マイクロ秒）を間違えると隙間や重なりができる
  • 半開区間なら 前の行の valid_to = 次の行の valid_from で一致するので、隙間も重なりも構造的に発生しない
  • 引くときも event_ts >= valid_from and event_ts < valid_to で、境界がちょうど 1 行に当たる

(3) 現在行の valid_to は null か 9999-12-31 か

方式 良いところ 面倒なところ
null 「まだ終わっていない」を型で表現できる。誠実 範囲検索が (valid_to is null or ts < valid_to) になる
9999-12-31 範囲検索が ts < valid_to だけで済む。BI に優しい 未来日として集計や軸に紛れ込む。番兵値の宗教論争が起きる
is_current 最新行の抽出が最速。クラスタリングも効かせやすい 冗長。更新漏れで valid_to と矛盾しうる

実務では is_current を併せ持つ構成が多い。 冗長ではあるが、ディメンションの用途の大半が「今の姿を引く」であり、where is_current の一行で済む効きが大きい。
矛盾のリスクは、後述のとおり閉じる / 足すを同一ステートメント（1 つの merge）で完結させることで抑える。

ファクトからどう引くか

同じ表から 2 つの見え方が取れる。ここが Type 2 を入れる唯一の理由と言ってよい。

-- as-was: 注文が起きた「当時」のプランで集計する
select d.plan, sum(f.amount)
from `dwh.fact_order` as f
join `dwh.dim_user` as d
  on  d.user_id = f.user_id
  and f.ordered_at >= d.valid_from
  and (d.valid_to is null or f.ordered_at < d.valid_to)
group by d.plan;

-- as-is: 「現在」のプランで過去の注文も塗り直して集計する
select d.plan, sum(f.amount)
from `dwh.fact_order` as f
join `dwh.dim_user` as d
  on d.user_id = f.user_id and d.is_current
group by d.plan;

Important

この 2 つは違う数字を返す。そして、どちらも正しい。
「当時 free だったユーザーの売上」を見たいのか、「今 pro になっている人たちが過去にいくら払ってきたか」を見たいのか。
Type 1 で運用していると 前者を選ぶ権利がそもそも無い（後者しか作れない）というのが、Type 2 の実質的な価値。

BigQuery で実装する（merge）

Warning

以下の SQL は実際の BigQuery プロジェクトで実行して検証したものではない。構文と挙動はドキュメントに当てて書いているが、動かす前に自分のデータセットで空振りさせること。

変更検知はハッシュで

追跡対象の列をまとめてハッシュ化し、現在行のハッシュと突き合わせる。列を 1 つずつ != で比較すると null の扱いで漏れるので、to_json_string を通してから畳むのが楽。

to_hex(md5(to_json_string(struct(plan, department, region)))) as row_hash

to_json_string は null も "null" という文字列として畳んでくれるので、concat のように「1 列でも null があると全体が null」にならない。

merge の壁 — 1 つの source 行は update か insert の片方にしか行けない

Type 2 の 1 回の変更は「既存行を閉じる（update）」と「新しい行を足す（insert）」の 2 アクション。
ところが merge の意味論では、source の 1 行は on に**当たれば when matched（update）、当たらなければ when not matched（insert）**のどちらか一方にしか流れない。1 行のままでは両方は起こせない。

そこで、変更 1 件を「閉じる行」と「足す行」の 2 行に分解し、閉じる行にだけ結合キーを入れる。

-- ① 差分を「閉じる行」と「足す行」に仕分ける
create temp table staged as
with src as (
  select
    user_id
    , plan
    , department
    , to_hex(md5(to_json_string(struct(plan, department)))) as row_hash
    , ingested_at
  from `raw.users_snapshot`
  -- source 側の重複は先に潰しておく（後述のエラー対策）
  qualify row_number() over (partition by user_id order by ingested_at desc) = 1
),
diff as (
  select
    src.*
    , cur.user_sk as target_sk        -- 既存の現在行の sk。新規ユーザーなら null
  from src
  left join `dwh.dim_user` as cur
    on cur.user_id = src.user_id and cur.is_current
  where cur.user_id is null           -- 新規ユーザー
     or cur.row_hash != src.row_hash  -- 属性が変わったユーザー
)
-- 閉じる行: 既存の現在行がある場合だけ作る。merge_sk が入っているので必ず当たる
select 'close' as change_type, target_sk as merge_sk, diff.*
from diff where target_sk is not null
union all
-- 足す行: merge_sk が null なので何にも当たらない
select 'insert' as change_type, cast(null as string) as merge_sk, diff.*
from diff;

-- ② 1 つの merge で「閉じる」と「足す」を同時に起こす
merge `dwh.dim_user` as t
using staged as s
on t.user_sk = s.merge_sk

when matched and s.change_type = 'close' then update set
  valid_to   = s.ingested_at,
  is_current = false

when not matched and s.change_type = 'insert' then insert (
  user_sk, user_id, plan, department, row_hash, valid_from, valid_to, is_current
) values (
  generate_uuid(), s.user_id, s.plan, s.department, s.row_hash, s.ingested_at, null, true
);

読みどころは 2 つ。

  • 結合キーを user_sk（行ごとに一意）にしている。 user_id で当てると「1 target 行に複数 source 行」の危険が出る
  • 新規ユーザーには閉じる行を作らない。 where target_sk is not null を落とすと、閉じる行も when not matched に流れて同じ行が 2 回 insert される

そして閉じると足すが同一ステートメント内で起きるので、「閉じたが足す前に落ちて現在行が消えた」という中途半端な状態にならない。is_current と valid_to の矛盾を防ぐのはこの原子性。

Note

change_type で when 句を出し分けるこの形は、dbt が snapshot_merge マクロで実際に使っている構造（dbt 側は dbt_change_type という列名）。自分で書く場合も、素直に真似ておくと事故が減る。

Warning

UPDATE/MERGE must match at most one source row for each target row
source 側に同じキーの行が複数あると実行時に落ちる。1 つの target 行に対して複数の source 行が当たったとき、BigQuery はどちらを採用するか決められないため。
逆向き（1 source 行 → 複数 target 行）は許される。source の重複だけが問題なので、qualify row_number() で先に 1 行に絞るのが定石。dbt snapshot でこのエラーが出る場合も、原因は unique_key が source で一意になっていないこと。

パーティションとクラスタリング

Type 2 のディメンションは行数が「実体数 × 変更回数」で膨らむので、当てておく。

create table `dwh.dim_user` (...)
partition by date(valid_from)
cluster by user_id, is_current;
  • partition by date(valid_from) … 行が追加される側で切る
  • cluster by user_id, is_current … where is_current と user_id 結合の両方が効く

なお merge の on に絞り込みが無いと、target 側は全パーティションを見にいく。ロード対象の期間が分かっているなら and t.valid_from >= @since のような条件を on に足してスキャンを絞る。

dbt で実装する（snapshot）

dbt は Type 2 を snapshot という専用のリソース種別として組み込みで持っている。上の merge を自分で書く必要がなくなる。

定義（dbt Core 1.9 以降は YAML） 

# snapshots/users_snapshot.yml
snapshots:
  - name: users_snapshot
    relation: source('raw', 'users')
    config:
      schema: snapshots
      unique_key: user_id
      strategy: timestamp
      updated_at: updated_at

Note

dbt 1.8 以前は SQL ファイル + Jinja の {% snapshot %} ブロックで書いていた。1.9 で YAML 定義が標準になり、旧形式は「Legacy snapshot configurations」として別ページに退避されている。ネット上のサンプルは旧形式のものがまだ多いので、拾ってきたコードが動かないときはここを疑う。

変更検知の 2 つの strategy

strategy 検知方法 必要な設定 使いどころ
timestamp updated_at 列が前回より進んでいるか updated_at 推奨。列の増減にも自動で追従する
check 指定した列の値が前回と違うか check_cols（列リスト / all） 信頼できる更新日時列が source に無いとき

check は上で自分で書いた row_hash の比較と同じことをしている。timestamp が使えるならそちらのほうが安い。

dbt が付けるメタ列

列名 中身
dbt_scd_id スナップショット行ごとに一意なキー（＝サロゲートキー）
dbt_valid_from この行が有効になった時刻
dbt_valid_to 無効になった時刻。現在行は既定で null
dbt_updated_at 挿入時点の source 側の更新時刻
dbt_is_deleted 削除フラグ。hard_deletes = 'new_record' のときだけ付く

つまり dbt の既定は「is_current 列を持たず、dbt_valid_to is null を現在行とみなす」設計。
番兵値が欲しい場合は 1.9 以降の dbt_valid_to_current で変えられる。メタ列の名前自体も snapshot_meta_column_names で置き換えられる。

config:
  dbt_valid_to_current: "to_date('9999-12-31')"
  snapshot_meta_column_names:
    dbt_valid_from: valid_from
    dbt_valid_to: valid_to

source から行が消えたとき（hard delete）

自前実装で一番忘れるのがここ。source からレコードが物理削除された場合、何もしないとその行はずっと is_current = true のまま生き残る。

hard_deletes 挙動 版
ignore 何もしない（既定） 1.9+
invalidate 削除された行の dbt_valid_to を埋めて閉じる 1.9+
new_record dbt_is_deleted = True の行を新しく足して履歴に残す 1.9+

1.8 以前は真偽値の invalidate_hard_deletes で、1.9 で上記 3 択に置き換わった（旧設定は非推奨）。

Dataform で実装する

結論から言うと、Dataform に dbt の snapshot に相当する組み込みは無い。

  • 公式パッケージ dataform-co/dataform-scd が Type 2 用のモデルを提供していた（scd_valid_from / scd_valid_to を持つビューと、変更履歴を貯める incremental table を生成する）
  • ただしこのリポジトリは 2026-04-19 にアーカイブされ、read-only になっている。最後の push は 2024-02-02
  • したがって今から Dataform で Type 2 を組むなら、上の merge を自分で書くのが現実的な選択肢

Dataform 側で使える道具は type: "incremental" の incremental table で、これは SCD 専用機能ではなく汎用の差分更新。

config {
  type: "incremental",
  uniqueKey: ["user_sk"],
  bigquery: {
    partitionBy: "date(valid_from)",
    clusterBy: ["user_id", "is_current"],
    updatePartitionFilter: "valid_from >= timestamp_sub(current_timestamp(), interval 90 day)"
  }
}

押さえること。

  • uniqueKey を設定すると、Dataform は append ではなく merge を発行する。 設定しないと単なる追記になる
  • updatePartitionFilter は uniqueKey があるときだけ効く。 uniqueKey 無しで指定しても insert 戦略のままになり、意図した枝刈りが起きない
  • type: "incremental" は when(incremental(), ...) で必ず where 句を持つ必要がある。これは source 側の枝刈りで、updatePartitionFilter（target 側の枝刈り）とは別物
  • スキーマ変更時の挙動は FAIL / EXTEND / SYNCHRONIZE から選ぶ。SYNCHRONIZE は列の削除を伴い、取り消せない

とはいえ incremental table の merge は「キーが一致したら更新、しなければ挿入」という 1 対 1 の更新モデルなので、Type 2 の「閉じる + 足す」をそのまま表現できない。
素直にやるなら operations で merge を直接書くか、「変更履歴を追記する incremental table」＋「そこから lead() で valid_to を計算するビュー」の 2 段構成（dataform-scd が取っていた形）に寄せることになる。

観点 手書き merge dbt snapshot Dataform

採否の判断軸

全部のディメンションを Type 2 にするのは誤り。 行数と運用負荷が増えるだけで、履歴を誰も見ない表がほとんどだから。次の順で切る。

  1. その属性で「過去のある時点」を切りたい要求が実在するか。 「いつか要るかも」は要らない。実在するレポート・実在する問い合わせがあるか
  2. 変更は訂正か、事実の変化か。 訂正なら Type 1。過去も間違っていたのだから、遡って直るのが正しい
  3. 変更頻度はどれくらいか。 毎日変わる属性を Type 2 にすると行数が爆発する。その場合は Type 4（ミニディメンション）に切り出すほうが筋がよい
  4. 代替手段で足りないか。 ファクト側に発生時点の値をそのまま焼き込む（非正規化）で済むなら、ディメンションを Type 2 にする必要はない
  5. 自分の現場の事情（対象テーブル・要求元・運用体制）を最後に当てる

Tip

Type 1 で運用していた表を後から Type 2 に変えることはできるが、変える前の履歴は永久に取り戻せない。
迷ったときは「今すぐ Type 2 の表を作る」ではなく「source のスナップショットを日次で貯めておく」でも保険になる。後から lead() で有効期間を組み立て直せる。

よくある落とし穴

  • is_current と valid_to が矛盾する … 閉じると足すを別ステートメントに分けると、片方だけ成功した状態が生まれる。1 つの merge で完結させる
  • source の重複を潰していない … UPDATE/MERGE must match at most one source row で落ちる。qualify row_number() で先に絞る
  • hard delete を忘れる … source から消えた行が永久に「現在」であり続ける
  • null を含む列をハッシュ化していない … concat は 1 列でも null があると全体が null になり、変更を検知できない。to_json_string を通す
  • 有効期間を閉区間で組んだ … 粒度の差で境界に隙間や重なりができる。半開区間 [from, to) にする
  • BigQuery の time travel を履歴保持と混同する … あれは最大 7 日の運用機能であって、テーブル設計としての履歴ではない（cf. BigQuery Data Quality）
  • タイムゾーン … valid_from を date で持つと JST / UTC の境界で 1 日ずれる。timestamp で持って表示側で寄せる
