[gh] RUN 活用の違い

gh workflow run が正しく、gh run workflow は NG (とゆうか打てない)。

gh のコマンド体系は gh <サブコマンド群> <動詞> なので、語順を入れ替えると別物になる。

コマンド 意味
gh workflow run <file> ワークフローを実行する（workflow グループの run 動詞）
gh workflow list / view / enable / disable ワークフロー定義の一覧・参照・有効化
gh run list / view / download / watch / rerun / cancel / delete 実行済み run の一覧・参照・artifact 取得など
gh run workflow ... 存在しない。 unknown command "workflow" for "gh run" で落ちる

つまり run は、gh workflow の下では「動詞（実行する）」、gh run では「名詞（実行結果 = run）」として使われている。ここが紛らわしいところ。

実際に叩くとこうなる。

$ gh run workflow
unknown command "workflow" for "gh run"

Usage:  gh run <command> [flags]

Available commands:
  cancel
  delete
  download
  list
  rerun
  view
  watch

--help で見ても、説明文からして持ち場が違う。

$ gh workflow --help
List, view, and run workflows in GitHub Actions.
...
AVAILABLE COMMANDS
  disable:       Disable a workflow
  enable:        Enable a workflow
  list:          List workflows
  run:           Run a workflow by creating a workflow_dispatch event
  view:          View the summary of a workflow

$ gh run --help
List, view, and watch recent workflow runs from GitHub Actions.
...
AVAILABLE COMMANDS
  cancel:        Cancel a workflow run
  delete:        Delete a workflow run

  list:          List recent workflow runs

  view:          View a summary of a workflow run

覚え方としては、

  • これから走らせる → gh workflow run
  • 走った結果を見る / 落とす → gh run view / gh run download

なお gh workflow run は workflow_dispatch イベントを作るコマンドなので、対象のワークフローが on: workflow_dispatch を持っていないと呼べない。

手元の dev/ci_gha.sh に残してあるメモもこの対応どおりで、

# [1] これから走らせる
$ gh workflow run anonymous-data-extract.yml ...

# [2] 走った結果の artifact を落とす
$ gh run download 32833987 --name stats-client-20260828 ...

になっている。

[gh api] environment の id を調べて deployment を承認する

environment に protection rule が付いていると、run は途中で waiting（承認待ち）に入って止まる。これを CLI から通すには environment の id（integer） が要る。name（qa など）では通らない。

調べ方は 2 通りある。

方法 1: 承認待ちの run から引く（推奨） 

$ gh api repos/OWNER/REPO/actions/runs/<run-id>/pending_deployments \
    --jq '.[] | "\(.environment.id)\t\(.environment.name)"'

その run が実際に待っている environment だけが返るので、取り違えない。

そもそも pending_deployments のレスポンスには最初から id が入っていて、自分が name しか表示していなかっただけだった。id を別で探しに行く前に、手元のレスポンスを全部出す。

方法 2: リポジトリの environment 一覧から引く 

$ gh api repos/OWNER/REPO/environments \
    --jq '.environments[] | "\(.id)\t\(.name)"'

qa / production が並んで出る。id はリポジトリ固定なので、一度控えておけば次回から使い回せる。

承認まで通しで 

RUN=<run-id>

# [1] qa の environment id を拾う
ENV_ID=$(gh api repos/OWNER/REPO/actions/runs/$RUN/pending_deployments \
  --jq '.[] | select(.environment.name=="qa") | .environment.id')
echo "qa env id = $ENV_ID"

# [2] 承認する
gh api -X POST repos/OWNER/REPO/actions/runs/$RUN/pending_deployments \
  -F "environment_ids[]=$ENV_ID" -f state=approved -f comment=''

ハマったのは 2 点。

指定 挙動
-F "environment_ids[]=$ENV_ID" 正しい。 -F は値を型付きで送る（数字は integer になる）ので API に通る
-f "environment_ids[]=$ENV_ID" NG。 -f は常に文字列として送るため、integer 配列を期待する API に弾かれる
-f comment='' 必須。 空文字で構わないが、キーごと省略すると 422 Unprocessable Entity になる

Note

-f / -F の使い分けは gh api 全体の話で、この API に限らない。state=approved のような素の文字列は -f でよく、integer や boolean を求められる項目だけ -F に上げる。

承認が通ると run が waiting → in_progress に変わり、migrate-backend-qa → deploy-backend-qa → verify-deployment-qa と流れていった。
