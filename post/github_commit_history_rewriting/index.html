Why

SSIA

作業に集中していると、コミットは大抵きれいに積み上がらない。 「3つ前のコミットに入れ忘れがあった」「WIP コミットが5個並んでいる」——レビューに出す前に気づくやつ。

git commit --amend は HEAD 専用 なので、途中のコミットには効かない。 そこで必要になるのが --fixup + rebase --autosquash を中心とした 履歴整形の手札 で、これを毎回ググらずに済むようまとめておく。

What

0. 前提：いつ書き換えてよいのか

Warning

履歴の書き換えは コミットの SHA が変わる 操作。 「自分しか触っていない範囲か」を先に確認する。

対象 書き換え 補足
ローカル未 push ⭕️ 自由にやってよい
自分の feature ブランチ（push 済み） ⭕️ --force-with-lease で上書き
他人がチェックアウトしている feature ⚠️ 一声かけてから
main / develop などの共有ブランチ ❌ やらない

また、未コミットの変更がある状態で rebase を始めない。 先に git status を見て、退避するなら stash に逃がしておく。

# コミット一時退避
% git stash && git stash list
% git stash apply stash@{0}
% git stash drop stash@{0}

Caution

git checkout <dir> / git restore のような破壊的コマンドを「挙動確認のため」に実作業ツリーで試さないこと。 git add すらしていない変更は Git の管理下に無いので、reflog でも戻せない。 検証したいなら git clone /path/to/repo /tmp/x で一時クローンを作ってそこでやる。

1. HEAD を直す — git commit --amend

直前のコミットに対してだけ有効。メッセージの打ち間違い、ファイルの入れ忘れはこれで足りる。

# 今のコミットメッセミスった?!
% git commit --amend --date=now -m "..."

# ファイルの入れ忘れ（メッセージは据え置き）
% git add forgotten.md
% git commit --amend --no-edit

2. 過去のコミットに畳み込む — --fixup + --autosquash

HEAD ではない 途中のコミットに、後から変更を畳み込む 方法。 --amend は HEAD 専用なので、過去コミットには --fixup + rebase --autosquash を使う。

# 例) config.yaml の修正を、過去コミット 7c6ed4a4 に合流させたい
#     (後続コミット dc2569c2 / dabcda88 はそのまま上に載り直る)

# [1.] 修正をステージ
% git add config.yaml

# [2.] 対象コミット宛の fixup コミットを作成 (メッセージは自動で "fixup! ...")
% git commit --fixup=7c6ed4a4

# [3.] autosquash で畳み込む (対象の 1 つ前 "~1" を base に指定)
% git rebase --autosquash 7c6ed4a4~1

#   ↑ エディタを開かず流したい場合:
% GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash 7c6ed4a4~1

# （万一おかしくなったら中止して元に戻す）
% git rebase --abort

Tip

  • git commit --fixup=<hash> … 対象コミットに紐づく fixup! コミットを作るだけ（この時点では畳み込まれない）
  • git rebase --autosquash <base> … fixup! を対象直後に自動並べ替え＆squash。<base> は 対象の 1 つ前 を渡す
  • git config --global rebase.autosquash true を入れておくと -i 時に常時 autosquash が効く
  • メッセージも書き換えたい場合は --fixup ではなく --squash=<hash>

--fixup の良いところは、畳み込み先を決めるのがコミット時点であること。 後から rebase -i の画面で「どれをどこに入れるんだったか」を思い出さなくて済む。

3. 複数コミットをまとめる — rebase -i + squash

WIP が並んでしまった場合はこちら。

# [1.] コミットの整理整頓 (開発中ブランチにて)
% git rebase -i master

# （万一中断する場合：rebaseを中止して元に戻す）
# % git rebase --abort

# [2.]
# [2-1.] 修正ファイルが立ち上がる pick から纏めたい履歴を「[s]squash」に変更
#. pick 316b8f1 # empty: 2026-01-19
#. s    b75acb7 # modify: views/covid_19/base_data.lkml...
#. s    44675ca # create: dashboards/covid-19...
#       (行の並び順を変えることもできる。しかし依存関係に注意)
# ---:wq
# [2-2.] 次に開くエディタでコミットメッセージを編集
#      統合後のコミットメッセージを書く画面が開く
#      不要なメッセージを削除し、1つの分かりやすいメッセージにまとめる
# ---:wq
コマンド 挙動
pick そのまま残す
reword 内容はそのまま、メッセージだけ書き換え
squash (s) 直前のコミットに統合（メッセージは編集させられる）
fixup (f) 直前のコミットに統合（メッセージは捨てる）
drop (d) そのコミットごと捨てる

一番上の行は統合先なので squash にできない、という点だけ注意。

4. 事故ったときに戻す 

# rebase の途中で詰んだ → まず中止
% git rebase --abort

# rebase が終わってしまった後で「やっぱり戻したい」
% git reflog                       # 書き換え前の HEAD を探す
% git reset --hard HEAD@{5}        # その時点に戻す

reflog は 一度でもコミットされた状態 なら追える。 逆に言えば、コミットしていない作業ツリーの変更は追えない（→ 0. の警告）。

5. そもそも書き換えを減らす前準備

コミット粒度を作る 

# 指定以外を全部コミット対象にする (指定ディレクトリを除外)
% git add -- . ':!TASK/ :!CONT/'

# 対話的に hunk 単位で選ぶ
% git add -p

Conventional Commits 形式

接頭辞を英語の動詞ベースに揃える。チーム内で意味が伝わりやすい為よく使われる。

feat:     （機能追加）
fix:      （バグ修正）
refactor: （構造変更）
docs:     （ドキュメント）
test:     （テスト）
chore:    （雑務）
  • 「修正」用途であれば edit: よりも fix: を使う方が、修正＝不具合対応だとすぐに理解できる。軽微な調整やリブランド用途なら chore: や style: を定義しておく手もある。
  • Prefix の定義は README などに明文化しておき、チーム全員が同じ語彙を使うようにするとレビュー時の判断が楽になる。
  • 日本語由来の用語を使う場合でも、プレフィックスは 短い英単語＋コロン で統一するとツール連携や外部コントリビューターにも伝わりやすい。

6. push で上書きする 

# 他の人が同時にpushしていないかチェックしてから上書き（より安全）
% git push --force-with-lease origin feature/jira-4944

--force は相手の push を無条件に踏み潰す。 --force-with-lease は 自分が最後に見たリモートの状態と違っていたら弾いてくれる ので、常にこちらを使う。
