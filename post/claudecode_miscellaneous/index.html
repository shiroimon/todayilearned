/branch /fork /subtask の使い分け

2026/08/10 追記 の補足。 3つとも「今のコンテキストを持ったまま別の作業を走らせる」点は同じ。違うのは 自分がどこに残るか と 結果がどこに返るか の2点だけ。

観点 /branch /fork /subtask
自分の居場所 分岐先へ移る 今の会話に残る 今の会話に残る
相手 元の SS が凍結（保存） コピーが background session として走る サブエージェントが走る
プロセス 同じ 別 同じ
結果の行き先 分岐先の会話にそのまま 向こうの会話（自分で見に行く） この会話に返ってくる
戻る導線 /resume <元の名前> 走行中は claude attach <id>
/ 終了後は /resume		 不要（勝手に返る）
/resume の一覧 出る 出る（bg 表示） 出ない（sidechain）

Tip

雑に選ぶなら、

セッションをまたいで行き来したい          → /branch
別トピックを並走させ、自分で取りに行く    → /fork
結果をこの会話に報告させたい              → /subtask
  • /branch は公式ドキュメントにも Switches you into the branch and preserves the original, which you can return to with /resume と書かれている。元に戻ることが前提の機能。
  • /fork の background session も /resume の一覧「には」出る（bg 表示）。ただし走っている間は resume で掴めず、Session <id> is already running — claude attach <id> to join it と言われる。 生きている background session に入る導線は agent view（claude agents で一覧 → 選択、または claude attach <id>）。
  • /subtask <task> は Task tool のサブエージェントだが、空のコンテキストではなく今の会話を丸ごと引き継ぐのが普通の Task tool 委任との差。だから「さっきまで話してた前提」を説明し直さなくていい。
/fork 先の結論はいつ回収するのか

/subtask は「終わったら通知が来る」ので考えなくていい。問題は /fork で、向こうから声はかからない。回収は自分でタイミングを決める。

とはいえ投げっぱなしで消えるわけではなく、回収用の CLI が一式ある。/fork した直後に backgrounded <id> と一緒に導線が出る。

コマンド 用途
claude agents 走っている background session の一覧（--json もある）
claude logs <id> attach せずに直近の出力だけ覗く
claude attach <id> このターミナルで開いて中に入る
claude stop <id> 止める。会話は残るので後で claude attach <id>
claude rm <id> worktree ごと削除（stop と違い終了済みにも効く）
claude respawn <id> 今の Claude バイナリで再起動（--all 可）

回収の実際の運びは3択。

様子だけ見たい          → claude logs <id>     ← 一番使う。context を汚さない
方向を直したい          → claude attach <id>   ← 走行中でも入れる
終わってから読む        → /resume（picker に bg 表示）

claude logs が効くのが大きい。「気になったら覗く、まだなら放置」が attach なしでできるので、回収タイミングを決め打ちしなくていい。

忘れても致命傷にはならないようになっている。

  • 終了済みの session に attach しても Session <id> has exited; attach shows the captured output で、出力は残っている
  • 走っている bg があるまま親を終わらせようとすると ... still running. Run claude agents to see your background sessions. と言われる

Important

ただし本命の回収物は会話ではなくファイル。 /fork 先は同じ作業ディレクトリで走るので、向こうが書いたファイルはこちらから普通に見える。 「1 SS 1 task」が守れないとき に書いた「SS をまたいで運べるのはファイルだけ」がそのまま当てはまる。 逆に言えば、ファイルに落ちない仕事を /fork に投げると回収コストが跳ね上がる。それは /subtask の担当。

/resume の一覧に出てこないもの

「さっきの会話が picker に出てこない」ときは、たいてい下のどれかで落ちている。

落ちる条件 具体例
sidechain サブエージェント（Task tool）の会話
team 所属（teamName あり） Agent Teams の teammate
sessionKind が daemon daemon-worker 常駐プロセス
/loop で始めた SS

sessionKind が bg（= /fork の行き先）は落ちないので、一覧には並ぶ。

/fork の実体

CLAUDE_CODE_SESSION_KIND=bg を付けた別プロセスで claude --resume <transcript> --fork-session を起動しているだけ。CLI の --fork-session と地続き。

agent view の有無で /fork の意味が変わる
agent view /fork の挙動 引数
有効（既定） 会話のコピーを background session として起動（/subtask も生える） [prompt]（省略可）
無効 会話を引き継いだ background agent を spawn（サブエージェント扱い） <directive>（必須）

「無効」は CLAUDE_CODE_DISABLE_AGENT_VIEW=1 か設定の disableAgentView を入れた状態。 coordinator session では /fork も /subtask も使えず、Use /branch instead. と案内される。

Tip

無効側の /fork は実質 /subtask

バイナリを覗くと、/fork（agent view 無効版）と /subtask は同じ関数を呼んで同じ完了メッセージ forked <name> (<id>) を出している。登録されている description も裏返しの関係になっている。

コマンド description 引数
/fork（有効時） Copy this conversation into a new background session and keep working here [prompt]
/fork（無効時） Spawn a background agent that inherits the full conversation <directive>
/subtask Send a subagent off with your full context; its result comes back here <task>

つまり agent view を切ると /fork が /subtask に化ける。 逆に言えば agent view が有効な既定環境では、/fork（別セッション・返ってこない）と /subtask（サブエージェント・返ってくる）を自分で選ぶ必要がある。 なお /subtask は最初のターンの前には使えず、Cannot start a subtask before the first conversation turn になる（引き継ぐコンテキストが無いので当然）。

Note

公式ドキュメントに明記されているのは /branch の「元に戻れる」だけ。 /resume のフィルタ条件・/fork の起動方法・agent view による分岐・/subtask との等価性は v2.1.224 の実装を読んで確認したもの（将来変わりうる）。

「1 SS 1 task」が守れないとき

セッションは 1 タスクにつき 1 つ、とよく言われる（自分もそう勧めている）。ただ実際にやると、

  • 調査・裏取り（bq / DB を叩く系）
  • コード解析
  • feature 実装

このあたりは細分化しても、途中で「やはりこうしたい」「別の着眼点に気づいた」が頻繁に出てきて、1 タスクの輪郭が保たれない。

切る単位を task ではなく成果物にする

task は途中で変質するが、1 個のファイルを書き上げるは変質しない。 なので「1 SS 1 task」ではなく「1 SS 1 成果物」で切ると、途中で方向が変わっても線が引ける。

SS をまたいで運べるのはファイルだけ、と割り切るのも同じ話。 会話ごと持ち越そうとして /branch /fork に手が伸びるが、どちらもコピーなので context は 1 トークンも減らない。「引き継ぎつつ減らす」ができるのは /compact だけ。

3 種類を同じルールで扱わない
種類 context の性質 切り方
調査・裏取り（bq / DB） 入力が重く、残す価値は結論だけ 使い捨て。md に書いたら /clear
コード解析 読む量は多いが、結論は構造理解 使い捨て寄り。理解を書き出せば捨てられる
feature 実装 「今どこまで直したか」の状態を保つ必要がある 保持。分割しにくく、/compact で延命する場所

前 2 つは圧縮率が異常に高い（100k 読んで結論は 20 行）。実装は逆で、圧縮すると壊れる。 「セッションが重い」の大半は前 2 つなので、そこを使い捨てにするだけで実装用の窓が空く。

途中の「こうしたい」は 2 択で捌く

判別は 1 つだけ、今やっている作業の結論を変えるか。

今の結論を 対処
変えない その場で 1 行だけファイルに落として、今の線を終わらせる
変える 分割線が間違っていた証拠。今の線を畳んでそちらへ切り替える

大半は前者。ここで詰まるのは「落とす先が決まっていない」ときで、落とす先が無いから SS の中に留めようとして、結果セッションが太る。落とす先を先に 1 個決めておく（NOTES.md なり .inbox/ なり）。

Note

調査は「下書き用紙」、実装は「清書中の原稿」。 下書きは書き終わったら結論だけ写して捨てる紙で、取っておく紙ではない。 「1 SS 1 task」が苦しいのは、下書きも清書も同じ引き出しに入れようとしているから。

事前に細かく分割しても途中で崩れるのは失敗ではなく、調査系はやってみないと分割線が見えない性質。 事前分割より「成果物が 1 個できたら切る」という事後の切り方の方が合う。

SS（セッション）の運用

SS

  • セッション = プロジェクトディレクトリに紐づいた「保存された会話」のこと
  • 実体は ~/.claude/projects/<project>/<session-id>.jsonl
① SS に名前を付ける 
   plan mode   命名
    ↓           ↓
SS -+--(承認)-[hoge]------> /exit
                            | /resume hoge で復帰
                            └─-[hoge]----------->
  • plan mode (shift+Tab*2) で計画 → 【承認】 でここに命名が付く
  • プロンプトウィンドウにに色付きで [hoge] と表示される
  • 名前を付けておかないと後で /resume <name> で呼び出せない
② SS を呼び出す
コマンド 挙動
claude --continue カレントディレクトリの最新 SS を再開
claude --resume picker を開く
claude --resume <name> 名前指定でそのまま再開
/resume セッション中に別の会話へ切り替え
/resume <name> 名前指定で切り替え（曖昧ならエラー）

picker のショートカット：Space プレビュー / Ctrl+R リネーム / Ctrl+B 現在の git ブランチで絞る / Ctrl+W 全 worktree / Ctrl+A 全プロジェクト。

復元されるもの：会話履歴・モデル・agent・permission mode（ただし plan と bypassPermissions は復元されない）・アクティブな goal。 復元されないもの：--mcp-config --settings --plugin-dir --fallback-model --add-dir などの起動フラグ（再指定が必要）。

③ SS を分岐 
/branch :  SS ----+                    元の SS は凍結（保存はされる）
                  └─ SS' ------------> 自分はこっちへ移動する
                                       戻るには /resume <元の名前>

/fork   :  SS ------------------------> 自分はここに残る
                  └─ SS' -------------> コピーは background session として走る

  • /branch [name] : コピーを作って自分が切り替わる。

    • 名前省略時は会話の最初のプロンプトから命名。実行後に「新しい方」と「元の方」の 2 つの session ID が出る。
    • 同一プロセスのままなので Allow for this session の許可はそのまま引き継ぐ
    • 実行中の background subagent / background bash は分岐先に出力される（元には出ない）

  • /fork [prompt] : コピーを background session として起動

    • 自分は今の会話に残る。プロンプトを渡すとそのまま走り出す。picker では bg 表示。
    • v2.1.212+ が必要。agent view を切っていると 今のセッションにぶら下がるサブエージェントに(forked subagent) として動く

  • CLI からは claude --continue --fork-session / claude --resume --fork-session

    • こちらは別プロセスなので許可は引き継がれず、再承認が必要
④ SS 巻き戻す
  • /rewind、または入力欄が空の状態で Esc 2 回でメニューが開く。
  • 「会話を戻す」だけではなく、コードも戻せるのがポイント。
選択肢 効果
Restore code and conversation コードと会話の両方をその時点へ
Restore conversation 会話だけ戻す（コードは現状維持）
Restore code コードだけ戻す（会話は維持）
Summarize from here そこから先を要約に圧縮（コンテキスト節約）
Summarize up to here そこまでを要約に圧縮（以降はそのまま）

チェックポイントはユーザーのプロンプトごとに自動作成され、直近 100 件のスナップショットを保持。 会話と一緒に保存されるので /resume した後でも /rewind できる。

Warning

戻らないもの

  • bash コマンドによるファイル変更（rm mv cp など）→ 追跡対象外
  • サブエージェントの編集（foreground の forked skill を除く）→ git で戻すしかない
  • Claude Code の外で手動編集したファイル、別セッションの編集
  • symlink / hardlink のパス（Restored the code, but skipped N files と警告が出る）

あくまでセッション単位の応急処置。バージョン管理の代わりにはならない。

Subagent（Task tool）

単発の作業を委任する仕組み。（普段の会話で自然に使われている）

あなた: 「このプロジェクトのルーティング処理がどこにあるか調べて」

Claude（内部処理）: → 「探索タスクだな、Exploreエージェントに任せよう」 → Task tool で Explore サブエージェントを生成 → 結果を受け取って、あなたに回答

普通に会話しているように見えますが、裏でSubagentが動いてくれていいる。

明示的に指示するパターン

  特定のやり方を指定したい場合は、自然言語で伝えるだけ。

  # 並列で調査させたいとき
  「フロントエンドとバックエンドのエラーハンドリングを並列で調べて」

  # チームで作業させたいとき
  「チームを組んで、このリファクタリングを進めて」

  # 特定のエージェントタイプを使わせたいとき（上級者向け）
  「Bash エージェントでテストを回して」

Subagentの種類（参考）

  ┌─────────────────┬──────────────────────────────┐
  │      種類       │          得意なこと          │
  ├─────────────────┼──────────────────────────────┤
  │ Explore         │ コード検索・構造調査         │
  ├─────────────────┼──────────────────────────────┤
  │ Plan            │ 実装方針の設計               │
  ├─────────────────┼──────────────────────────────┤
  │ Bash            │ コマンド実行                 │
  ├─────────────────┼──────────────────────────────┤
  │ general-purpose │ 何でも（ファイル編集も可能） │
  └─────────────────┴──────────────────────────────┘

Claude: 「この調査はサブエージェントに任せよう」 → Task tool で1体のエージェントを生成 → 結果を受け取って終了（使い捨て）

  • 1つのタスクを投げて、結果を返してもらう
  • エージェント同士の通信はない
  • 呼び出し元が結果を統合する
  • 普段の会話でも頻繁に使われている（Explore, Plan 等）

Agent Teams

Subagentを複数束ねて、協調させる仕組み。

あなた：1つのセッションで「チームで作業して」と指示するだけ。

Claude (リーダー): → TeamCreate でチーム作成 → Task tool で複数の teammate を生成（=各々がSubagent） → 共有タスクリスト + SendMessage で相互連携 → リーダーが管理・統合

  • 複数のSubagentがチームとして動く
  • 共有タスクリスト（TaskCreate/TaskList）で作業を管理
  • SendMessageでエージェント間通信ができる
  • ライフサイクルが長い（複数タスクをこなす）

両者は実は同じ仕組みの上に成り立っているもので、使い分けのレベルが異る。

関係図:

  Agent Teams
   └── teammate A  ← Subagent（Task tool で生成）
   └── teammate B  ← Subagent（Task tool で生成）
   └── teammate C  ← Subagent（Task tool で生成）
        ↕ SendMessage で相互通信
        ↕ TaskList を共有

一言でまとめると

  ┌────────────┬────────────────────────┬────────────────────────┐
  │            │        Subagent        │      Agent Teams       │
  ├────────────┼────────────────────────┼────────────────────────┤
  │ 規模       │ 1体                    │ 複数体                 │
  ├────────────┼────────────────────────┼────────────────────────┤
  │ 通信       │ なし（結果を返すだけ） │ あり（メッセージ交換） │
  ├────────────┼────────────────────────┼────────────────────────┤
  │ タスク管理 │ なし                   │ 共有タスクリスト       │
  ├────────────┼────────────────────────┼────────────────────────┤
  │ 用途       │ 単発の調査・作業       │ 複雑な協調作業         │
  └────────────┴────────────────────────┴────────────────────────┘

Subagentは部品、Agent Teamsはそれを組み合わせたチーム体制という関係

Claude Code MCP設定ガイド

設定ファイルの優先順位（強い順）

優先度 スコープ ファイル
1 Managed /Library/Application Support/ClaudeCode/managed-mcp.json
2 Local ~/.claude.json > projects.{パス}.mcpServers
3 Project プロジェクトルートの .mcp.json
4 User ~/.claude.json > グローバル mcpServers
  • 同名サーバーは上位スコープが完全に勝つ（マージされない）
  • 名前が異なればすべて共存する

各ファイルの役割

~/.claude/settings.json

  • 環境変数、モデル設定、プラグイン設定など
  • MCPの定義は含まない

~/.claude.json

  • Claude Codeの統計情報・プロジェクト管理情報
  • MCP設定は2箇所に書ける（スコープが異なる）
  • mcpServers（ルート直下）→ User スコープ：全プロジェクト共通
  • projects.{パス}.mcpServers → Local スコープ：特定プロジェクトのみ
  • 注意: Claude Codeプロセスが随時書き込むため、手動編集時は競合に注意

.mcp.json（プロジェクトルート）

  • Project スコープ：そのディレクトリ配下で起動した場合に有効
  • VCS管理でチーム共有が可能
  • ${VAR} 形式の環境変数展開をサポート

現在の構成

MCP定義は ~/Sandbox/MDE/.mcp.json に集約済み。 ~/Sandbox/MDE/ 配下で起動した場合のみ有効。

.claude/settings.jsonと.claude/settings.local.json` の違い

settings.json settings.local.json
用途 チーム共有のプロジェクト設定 個人用のローカル設定
Git コミット対象 自動で gitignore される
典型的な内容 チーム共通のMCPサーバー、権限ポリシー、hooks 個人のMCP追加/除外、マシン固有設定

優先順位（高い順）：

  1. Managed settings（組織管理）
  2. コマンドライン引数
  3. .claude/settings.local.json（ローカル）
  4. .claude/settings.json（プロジェクト）
  5. ~/.claude/settings.json（ユーザーグローバル）

ローカル設定がプロジェクト設定より優先されるので、 たとえばチームで共有しているMCPサーバーを個人的に無効にしたい場合は settings.local.json で上書きできる。

MCPの使い分けに活用する場合：

  • チーム全員が使うMCPサーバー → settings.json に定義
  • 自分だけ追加/無効にしたいMCPサーバー → settings.local.json で上書き

この仕組みを使えば、普段不要なMCPサーバーをローカル設定で無効にしておき、 必要なときだけ有効に戻す運用ができる。

セットアップ プロンプト

ccstatuslineをインストールして、見やすい監視機能を設定してください。

以下の手順で実行してください：

1. ~/.claude/settings.json を確認して、現在の設定を表示
2. ccstatuslineの設定を追加（bunx ccstatusline@latestを使用）
3. 以下のウィジェットを含む推奨設定を提案：
   - モデル名
   - コンテキスト使用率（使用可能率）
   - セッションコスト
   - ブロックタイマー
   - 入力/出力トークン数
   - Gitブランチ

4. 設定を保存してClaude Codeの再起動方法を教えてください

元に戻す手順

# 復元
cp ~/.claude/settings.json.bak ~/.claude/settings.json
cp ~/.config/ccstatusline/settings.json.bak ~/.config/ccstatusline/settings.json

Slash Commands

よく使う Slash Commands

  • /insight : 自分のClaude Code使用状況を分析・可視化する
  • /debug : SKILLsをブラッシュアップしたい
  • /doctor :
  • /compact : 重要な情報だけを表示して、会話をすっきりさせる

トークン節約系 Slash Commands

  • /context : コンテキスト確認

  • /usage : 使用状況確認

  • /clear : 会話履歴をクリア

  • /resume : 会話履歴を再開

  • /export : 会話履歴をﾌｧｲﾙで出して、新しい会話に引き継ぐ小技

  • /rewind : 指定したターンまでコードと会話を巻き戻す（軌道修正）※Esc 2回でも開く

  • /branch : 今の会話のコピーを作って自分がそっちへ移る（軌道修正）

  • /fork : 今の会話のコピーを background session として起動し、自分はここに残る（並走）

  • /subtask : 今の会話を引き継いだサブエージェントに投げ、結果がここに返ってくる（委任）

  • /rename : セッションに名前を付ける（/resume <name> で呼び出せるようになる）

    → 詳細は 2026/08/10 追記 を参照

  • Planモード（Shift+Tab×2）: 計画を立ててから実装に向く

    • cf. Claude Codeですぐ制限にかからないようにするコツ Zenn
