What

0. 「境界」ではなく「目的」の話

レビューをどこまで AI に任せるかの線引きは Code Review Boundary に書いた。 あれは どう分担するか の話で、こちらは そもそも何のためにやっていたのか の話。

順番としては後者が先にある。目的が決まらないと、自動化の可否も決められない。

もし不具合を見つけるためだけなら、完全に自動化するべきだ。 しかしチーム内での知識共有や、設計思想の理解、後輩の育成も目的だったなら、簡単に自動化はできない。

1. 欠陥指摘はレビューの14%しかない

Microsoft の調査（Bacchelli & Bird, 2013）では、レビューコメントのうち 欠陥に関するものは14%。 50%以上が「代替案の探索」 に使われていた。

つまり、バグを見つけられなかったレビューは失敗ではない。 「なぜ B ではなく A にしたのか」を1件でも投げたなら、それが本来の 50% 側の仕事をしている。

Warning

14% を「だから欠陥検出は重要でない」と読むのは誤読。 これはコメントの件数分類であって、防いだバグの価値ではない。重大バグ1件は設計議論100件より価値があり得る。 使えるのは「主目的ではない」までで、しかも 2013年・Microsoft 社内・AI 以前の研究。

2. 「読めない」の原因の多くは、読む側にない

同じ Microsoft の 2016年調査（開発者911名）では、レビュアーが挙げた課題の上位3つが

  1. タイムリーなフィードバック
  2. レビューサイズ
  3. 変更の動機の理解

で、詳細な説明を常に書く開発者は26%だけだった。

残り74%の PR は、動機が書かれない状態でレビューに出ている。 「何をどう読めばいいか分からない」は、読解力の問題ではなく 入力の欠損。

diff を開く前に「これは○○を△△にする変更」と1行で書けるか試して、書けなければそれが最初の質問になる。 自分がレビューされる側に回ったときに「なぜ」を書いて26%側に入るのが、自分の手だけで完結する唯一の改善でもある。

3. AI は原因ではなく増幅器

ここが一番効いた指摘。

AI がコードレビューを破綻させたのではなく、これまで見過ごしてきた課題を無視できない状態にした。

Meta の実測（過去1年）:

指標 変化
コード行数 +106%
開発者あたりの月次差分 +51%
増加の起因 80%以上がエージェント型 AI
24時間以内のレビュー完了率 低下
大規模グループのレビュー待ち 数千件

さらに DX の分析では AI 作成の PR はサイズが64%大きい。

件数 × サイズで増えるので、レビュー負荷は 件数に比例では済まない。 1 PR が大きくなると全体像を掴むフェーズのコストが超線形に伸びる（2016年調査で「レビューサイズ」が課題の上位に来ているのはこの部分）。

そして記事の因果は「AI が悪い」ではない。 小さい差分に保つ・意図を書く、という基本習慣を守ってこなかったツケが、生成速度が上がって表に出た という話になっている。

Note

Meta / RADAR の数字（53.5万件処理、リバート率 1/3、本番事象 1/50、中央値クローズ 3.3倍高速）は Meta スケールの自動化投資の結果なので、自分のチームの参考値にはならない。物量の傾向だけ借りる。

4. 奪われたのは能力ではなく「余裕」

自分の実感に照らすと、「すごいな〜で終わる」も「理解しないまま LGTM」も AI 以前からあった。 ただし ここまでではなかった。

この「あったが、ここまでではなかった」が意味するのは、

  • 基本習慣（小さい PR・意図を書く）は 以前も守られていなかった
  • が、余裕があったから吸収できていた
  • 物量が倍になった時点で、基本習慣は選択ではなく 必須条件 に変わった

ということ。増幅器という説明は正しいが、記事は どこで耐えられなくなるか（閾値） を書いていない。 Meta の数字は物量を示せるが、閾値の存在は個人の証言でしか出てこない。

閾値を越えさせた機構の候補は3つ。

# 機構 中身
A 代償手段が払えなくなった 同期コストは件数に比例するが、使える時間は一定。「深く読む」選択肢自体が消える
B サイズの非線形化 1件あたりが64%大きくなり、全体像を掴むコストが超線形に伸びる
C 書き手が理由を持っていない 聞いても実装意図が返ってこない。「AI がそう書いたので」で止まる

5. 最初に失われたのは、欠陥検出ではなく学習経路

C が一番効いていると思う。

AI 以前は、書き手がコードの内部文脈を持っていた。だから「なぜ B ではなく A か」と聞けば答えが返ってきて、その答えが学びだった。 AI 生成コードでは書き手自身が全部を理解していない。

つまり CR の学習機能は、書き手が理由を持っていることに依存していた。 その前提が崩れると、正しい質問を投げても学べない。

これが「認知的負債・意図的負債」——システムの挙動と、組織がその理由を理解している範囲とのギャップ——の発生現場そのもの。 余裕が消えたとき最初に失われたのは 14% の欠陥検出ではなく、質問して答えが返ってくるという経路 の方だった。

知的オフロードは、誰も理解していないエラーにつながる可能性がある。 最終レビューを AI に完全委任はできない。承認には私の名前がついている。

6. 読む範囲の絞り方を変える

全部を薄く読む方向ではなく、一部を壊しにいく方向に振る。そのうえで絞る基準を差し替える。

  • 以前: 重要そうな箇所に絞る
  • 今: 書き手が理由を説明できる箇所に絞る

理由が返ってくる箇所は、読めば学びがあり議論も成立する。 理由が返ってこない箇所は、読んでも学びがなく、しかも認知的負債が最も溜まっている場所。 そこは「読んで理解する対象」ではなく 「誰も理解していないコードが入る」というリスク として扱う。

リスク層別化をツールではなく会話でやる、ということになる。

読む順序自体は変わらない。

  1. diff を開く前に、変更の目的を1行で書く（書けなければそれが最初の質問）
  2. git show --stat でファイル一覧だけ見る（テストが無い / 想定外のファイルが混じる、は中身より先に見える）
  3. 契約だけ読む（公開関数のシグネチャ、API、スキーマ）
  4. データの流れを代表1本だけ通す
  5. 境界（null / 空 / 0件 / 上限 / 並行 / 失敗時）を能動的に探す
  6. 残りは読まない。読まなかったと自覚する

7. LGTM の条件を自分で決める

「問題が見つからなかった」で LGTM しない。

条件 中身
壊しにいった痕跡が3つ言えるか 「A と B と C を壊しにいったが壊れなかった」
書き手が変更の理由を答えられたか 答えられないなら、コードの正しさとは別にリスクが残っている
読んでいない範囲を明示したか 「ロジックは見た、マイグレーションは見ていない」

3つ目は逃げではなく、レビューの範囲宣言。全部見た顔で承認するより誠実。

2つ目が満たせないときは、指摘ではなく事実として書ける。

動作は問題なさそうですが、この分岐の意図が私にも作者にも説明できていないので、そこはリスクとして残ります。

8. ここで立場が2つに割れる

同じ現象を、正反対に呼んでいる文章がある。

立場 「人間同士で理解し合うコスト」を何と呼ぶか
文化への違和感（前者） コスト。背景説明・文脈共有・認識合わせは重い。最小化すべき
What are CR for（後者） 本体。知識移転と集団的所有権こそ不可視の主目的。削れば認知的負債になる

前者は「レビューしていること ≠ 理解していること」「レビュアーにはコード表面しか見えない」と言う。これは実感として当たっている。 ただし その同期コストの正体は知識伝播 であって、削れば学びも一緒に消える。

後者の言い方だと「可視的出力は改善されたコード、不可視の出力はより優れた組織」になる。

AI は確実にレビュー時間を削減すべき。ただし学習量を削減してはいけない。

前者の診断（読む苦痛の構造）と、後者の処方（学習経路は守る）を分けて取るのが実際的だった。

Caution

後者の発行元（DX）は開発者生産性の計測を売るベンダー。 「スループットではなく学習効果を測定せよ」は自社製品の売り筋であり、測り方は書かれていない （junior の学習、アーキテクチャ知識の拡散、実質的な関与度の監視 —— 全部指標名だけ）。ここは借りられない。

9. 余談: 反応の分布も同じ構造をしている

この記事への SNS の反応を並べてみると、記事本文と逆のことを言っている反応が混じる。 「AI が骨子を作れるなら、見直しに時間を割けるのがメリット」——記事は「開発者がレビューに割ける時間は限られており、増やすのは現実的でない」と明言している側。

長い一次資料に対して、自分が既に持っている枠に収まる部分だけ取って承認する。 CR で起きていることと同型で、これがまさに「すごいな〜で終わる」の記事版になっている。
