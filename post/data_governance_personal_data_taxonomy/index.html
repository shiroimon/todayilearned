Why

データ基盤を触っていると、判断が必要な瞬間が定期的にやってくる。。
昨今あまりにセンシティブ故に、データの出方を間違えると「一発OUT！！！」になりかねない。

  • 「この users テーブル、分析チームの dataset にコピーしていい？」
  • 「アクセスログ、当初は障害調査目的で溜めてたけど、レコメンドの学習データに使い回していい？」
  • 「委託先ベンダに user_id をハッシュ化して渡せば、個人情報じゃないから自由？」
  • 「集計してマートにすれば、もう個人情報保護法の話は関係ない？」

これらは全部「そのデータが法律上どの箱に入っているか」で答えが変わる。
そして箱が決まると、テーブル分割・dataset 分離・IAM・Policy Tag・保持期間・データカタログのラベルまで一気に決まる。 逆に箱を曖昧にしたまま基盤を作ると、後から「この列だけ抜きたい」が地獄になる。

Note

個人情報保護法（令和3年改正 / 2022年4月1日全面施行）ベースの整理。
法的助言ではないので、実際の判断は必ず法務とガイドライン原文を突き合わせて行うこと。怖いね

What

TL;DR — 4つの箱 🗃️

🗃️箱 「ひとこと」で ⚖️法的な位置づけ 復元 第三者提供 主な用途
個人情報 誰の情報か分かる 個人情報（法2条1項） — 原則 本人同意 本来業務・本人への提供
仮名加工情報 単体では分からないが、照合すれば戻せる 独自カテゴリ（法2条5項・41条/42条） 可能 ❌ 原則不可（委託・共同利用のみ） 社内分析・AI学習
匿名加工情報 誰の情報か戻せない 個人情報ではない（法2条6項・43〜46条） 不可 ⭕️ 同意不要（公表・明示が条件） 社外提供・データ流通
統計情報 もはや個人単位ですらない 法の対象外 不可 ⭕️ 自由 BI・ダッシュボード・レポート

覚え方はシンプルに、

  • 仮名 ＝ 社内で使う。戻せる。だから外に出せない
  • 匿名 ＝ 社外に出せる。戻せない。だから加工基準が厳しい
  • 統計 ＝ そもそも個人の話じゃない。法の外

ベン図で位置関係を掴む

まずこの図が一番効く。

出典: STORIA法律事務所「仮名加工情報を利用したAI開発は可能か」

この図の読み方で、押さえるべきポイントが3つある。

(1) 個人情報と仮名加工情報は「重なる」（包含ではない）

ここが一番誤解されやすい。仮名加工情報は個人情報の部分集合ではない。重なりの正体は容易照合性。

状態 該当 適用条文
元データ・対応表を自社で保持 個人情報である仮名加工情報 法41条
元データ・対応表を削除／持たない 個人情報でない仮名加工情報 法42条

つまり「仮名加工したから個人情報じゃなくなる」は間違い。対応表を握っている限り、それは個人情報でもある。

(2) 匿名加工情報は個人情報の外にある

円が離れているのは「照合しても戻せない」から。
その代わり、後述するとおり加工基準が5要件と厳しく、公表義務までセットで付いてくる。

(3) 余白は「個人関連情報」

外枠は「生存する個人に関する情報」。3つの円のどこにも入らない余白が個人関連情報（法2条7項）で、定義がそのまま「個人情報・仮名加工情報・匿名加工情報のいずれにも該当しないもの」になっている。Cookie ID、広告 ID、閲覧履歴などがここ。

Important

個人関連情報は、提供先が個人データとして取得することが想定される場合、提供元は本人同意の確認が必要（法31条）。
CDP や広告連携で ID を外部に飛ばす構成は、ほぼ確実にここを踏む。

そして統計情報はこの外枠のさらに外にいる。ガイドライン通則編 2-8 が「統計情報は、特定の個人との対応関係が排斥されている限りにおいては『個人に関する情報』に該当するものではないため、個人関連情報にも該当しない」と明記している。

「生存する個人に関する情報」の内側
├── 個人情報
│   ├── 仮名加工情報でない個人情報              …… 通常の個人データ
│   └── 個人情報である仮名加工情報              …… 法41条
├── 個人情報でない仮名加工情報                  …… 法42条
├── 匿名加工情報                                …… 法43〜46条
└── 上記いずれにも該当しない残り = 個人関連情報 …… 法31条

「生存する個人に関する情報」の外側
└── 統計情報 ……………………………… 法の対象外

個人情報

定義（法2条1項）

号 内容
1号 氏名・生年月日その他の記述等により特定の個人を識別できるもの
他の情報と容易に照合でき、それにより識別できるものを含む（＝ 容易照合性）
2号 個人識別符号（法2条2項）が含まれるもの

個人識別符号の例: マイナンバー、運転免許証番号、パスポート番号、基礎年金番号、顔認証データ、指紋・虹彩・声紋データ。

データエンジニアが効かせるべきポイント

1号カッコ書きの「容易照合性」が全て。 ここを外すと設計が崩れる。

-- ❌ 「氏名を含まないから個人情報ではない」は成立しない
-- events テーブルに user_id しかなくても…
select user_id, event_name, ts from analytics.events;

-- …同じ事業者内に users テーブルがあり、join 一発で氏名に到達できるなら
--   events.user_id も「個人情報」として扱う必要がある
select
  e.user_id
  , u.full_name
from
  analytics.events e
  join core.users u using (user_id);

Warning

dataset / project を分けただけでは容易照合性は切れない。
「同一事業者内で通常の業務における一般的な方法で照合できるか」で判断されるため、IAM で塞いでいない別 dataset に置き換えただけでは論拠が弱い。切りたいなら対応表の物理的分離 ＋ IAM 分離 ＋ 運用ルールをセットで用意する。

派生カテゴリも押さえる

用語 定義 実務インパクト
個人データ 個人情報データベース等を構成する個人情報 安全管理措置・第三者提供規制の主対象
保有個人データ 事業者が開示・訂正・削除の権限を持つ個人データ 開示等請求（法33条〜）の対象 → 削除フローが必要
要配慮個人情報 病歴、健診結果、障害、犯罪歴等（法2条3項） 取得時に原則 本人同意。オプトアウト提供も不可

Tip

「要配慮個人情報を含むか」はテーブル単位ではなく列単位のメタデータで持つ。dbt なら meta に書いて、ドキュメントとアクセス制御の両方から参照できる形にしておくのが楽。

仮名加工情報

定義（法2条5項）

他の情報と照合しない限り、特定の個人を識別することができないように加工した個人に関する情報

令和2年改正で新設。個人情報と匿名加工情報の中間に位置するカテゴリ。

加工基準は3つだけ（規則31条）

号 加工内容
1号 特定の個人を識別できる記述等の全部または一部を削除／置換
2号 個人識別符号の全部を削除／置換
3号 不正利用により財産的被害が生じるおそれのある記述等を削除／置換
（クレジットカード番号、口座番号など）

匿名加工情報の5要件と比べると圧倒的に軽い。「特異な記述の削除」が要らないのが決定的で、外れ値・レアケースを保った高精度な分析ができる。

何が緩むか（法41条9項の適用除外）

緩む義務 条文 データ基盤へのインパクト
利用目的の変更制限 法17条2項 🔥 当初目的と関連性のない目的への転用が可能
漏えい等の報告・本人通知 法26条 インシデント時の報告義務が外れる（安全管理措置義務は残る）
開示・訂正・利用停止等の請求対応 法32〜39条 開示請求対応フロー・物理削除フローの対象外

最大の価値は1つ目。「障害調査目的で取得したログを、後から機械学習の学習データにする」が本人同意なしで可能になる。これはデータ基盤の設計自由度を大きく変える。

何が禁止されるか（法41条3〜8項 / 42条）

禁止／義務 内容
❌ 第三者提供 原則不可。委託・共同利用・事業承継のみ例外
❌ 識別目的の照合 本人を特定する目的で他の情報と突き合わせるのは禁止
❌ 本人への連絡・接触 DM 送信、電話、ターゲティング配信等はアウト
⚠️ 削除情報等の安全管理措置 対応表・削除した情報の安全管理（法41条2項・規則32条）
⚠️ 利用目的の達成に必要な範囲 変更は自由だが、設定した目的の範囲は守る

Caution

「仮名加工情報として扱う」と決めた瞬間、上記の義務がセットで付いてくる。
ハッシュ化して規制が消えるわけではなく、「規制の中身が別のものに差し替わる」だけ。DM 配信の母集団に使う予定があるなら、そもそも仮名加工情報にしてはいけない。

実装イメージ 

-- ① 対応表は別プロジェクト・別 IAM に隔離する（ここが 法41条2項 の安全管理措置）
create or replace table `prj-pii-vault.mapping.user_pseudonym` as
select
  user_id                                               -- 元の識別子
  , to_hex(sha256(concat(user_id, @salt))) as pseudo_id -- salt は secret manager から
from `prj-core.core.users`;

-- ② 分析側には pseudo_id しか流さない
create or replace table `prj-analytics.pseudo.events` as
select
  m.pseudo_id
  , e.event_name
  , e.ts
  , e.age  -- 「特異な記述」の削除は不要 → 119歳もそのまま保持できる
from
  `prj-core.core.events` e
  join `prj-pii-vault.mapping.user_pseudonym` m using (user_id);
-- 規則31条3号: カード番号など財産的被害リスクのある列は select に含めない
  • prj-pii-vault へのアクセス権を持つ人がいないのが理想（バッチのサービスアカウントのみ）
  • ただし自社が対応表を保持している以上、これは**「個人情報である仮名加工情報」（法41条）**である点を忘れない
  • 対応表を削除して初めて法42条側に移る

匿名加工情報

定義（法2条6項）

特定の個人を識別することができないように個人情報を加工して得られる個人に関する情報であって、当該個人情報を復元することができないようにしたもの

平成27年改正で新設。社外へのデータ流通を前提とした制度。

加工基準は5要件（規則34条）

号 加工内容 例
1号 特定の個人を識別できる記述等の削除 氏名、詳細な住所、生年月日
2号 個人識別符号の全部削除 マイナンバー、免許証番号
3号 情報を相互に連結する符号の削除 内部管理用の会員 ID、user_id
4号 🔥 特異な記述等の削除 「119歳」「年収3億円」「症例が極めて稀な病名」
5号 データベースの性質を踏まえたその他の措置 全国平均と大きく乖離する地域データの削除など

加工前後のイメージ

項目 加工前 加工後 手法
氏名 愛江 素雄 （削除） 削除
住所 東京都 ISO区 プロ2丁目 27001-2 東京都 一般化
年齢 31歳 30代 一般化（ビニング）
年収 475万円 450万円〜500万円 一般化（レンジ化）
職場 ISOプロ書店 小売店 一般化（カテゴリ化）

参考: ISOプロ「匿名加工情報とは」

付いてくる義務（法43〜46条）

義務 条文 備考
加工基準に従った作成 法43条1項・規則34条 5要件すべて
加工方法等情報の安全管理措置 法43条2項・規則35条 「どう加工したか」の情報自体を守る
作成時の項目公表 法43条3項・規則36条 含まれる個人に関する情報の項目を公表
第三者提供時の公表＋提供先への明示 法43条4項・規則37条 匿名加工情報であることを明示する義務
識別行為の禁止 法43条5項・法45条 提供元も提供先も、本人特定を試みてはならない
安全管理措置等 法43条6項・法46条 努力義務

Warning

「匿名加工情報にすれば自由に売れる」ではない。公表義務・明示義務・識別行為禁止が付いてくるので、パイプラインの外側に運用プロセス（公表ページの更新、契約書への明示条項）を作る必要がある。

実務での難しさ

4号の「特異な記述」に明確な閾値がないのが最大の壁。マーケティング分析では外れ値こそが示唆を持つことも多く、消すと分析価値が落ちる。

  • k-匿名性: 同じ属性の組み合わせが k 件以上になるよう一般化する（k=2, 5, 10 など）
  • l-多様性 / t-近似性: センシティブ属性の偏りにも配慮する拡張

Tip

ここが厳しいからこそ、社内利用なら匿名加工情報ではなく仮名加工情報を選ぶのが定石。
「社外に出す必要があるか？」を先に判定するのが設計の分岐点。

統計情報

位置づけ

個人情報保護法の適用対象外。「個人情報でない」だけでなく、そもそも**「個人に関する情報」ですらない**。

  • ガイドライン通則編 2-8: 「統計情報は、特定の個人との対応関係が排斥されている限りにおいては『個人に関する情報』に該当するものではない」
  • Q&A 1-17 付近: 複数人の情報から共通要素に係る項目を抽出し、同じ分類ごとに集計して得られる情報

Note

「特定の個人との対応関係が排斥されている限りにおいては」という条件節が本体。ここを満たさない集計は統計情報ではない。

落とし穴 — 集計しても安全とは限らない 

-- ⚠️ 集計しているが、n=1 のセルが「その個人の情報」を露出させる
select prefecture, disease_name, count(*) as n, avg(salary) as avg_salary
from patients
group by prefecture, disease_name;
-- → 「鳥取県 × 特定の希少疾患 × n=1」で個人が特定でき、
--    その人の年収まで avg() 経由で露出する（＝ 差分攻撃の入口）

対策の定番は3つ。

対策 内容
セル抑制（small cell） having count(*) >= k で小セルを落とす
粒度の一般化 都道府県 → 地方ブロック、日次 → 月次
差分プライバシー ノイズを付与して個体の寄与を隠す

BigQuery は差分プライバシーを SQL でネイティブに書ける。

select with differential_privacy
  options (epsilon = 10, delta = .01, privacy_unit_column = user_id)
  prefecture
  , count(*, contribution_bounds_per_group => (0, 100)) as n
from `prj-analytics.core.patients`
group by prefecture;
オプション 意味
privacy_unit_column 保護対象エンティティの一意識別子（＝ 個人）
epsilon プライバシー予算。小さいほど強い保護 ＝ ノイズ大
delta 保護が破れる確率の上限
contribution_bounds_per_group 1人がグループへ寄与できる上限（クリッピング）
max_groups_contributed 1人が寄与できるグループ数の上限

委託と統計情報

委託先が委託元から預かった個人データを統計情報に加工する論点は Q&A 7-36 付近で整理されている。ざっくり言うと委託された業務の範囲内であれば可能で、統計情報化した後の情報は法の規制を受けない。
ただし「複数の委託元のデータを混ぜる」「委託先が自社目的で使う」は委託の範囲を超えやすいので、契約に何を書いたかで決まる。

データ基盤への落とし込み

レイヤ設計

法的カテゴリをそのままレイヤ境界にするのが、結局いちばん壊れにくい。

レイヤ 法的カテゴリ 配置 アクセス権
raw / core 個人情報 prj-core 業務システム連携のみ
mapping 対応表（要保護） prj-pii-vault（単独プロジェクト） サービスアカウントのみ
pseudo 仮名加工情報 prj-analytics 分析チーム
anon 匿名加工情報 prj-share 外部提供パイプライン
mart 統計情報 prj-bi 全社

BigQuery の道具

目的 機能
列単位のアクセス制御 Policy Tag（列レベルセキュリティ）
列の値を隠す（権限で切替） Dynamic Data Masking（Policy Tag ＋ データポリシー）
行単位の絞り込み Row-level security（create row access policy）
元テーブル権限なしで集計を見せる Authorized View / Authorized Dataset
統計情報のノイズ付与 select with differential_privacy
保持期間の強制 テーブル / パーティションの expiration

マスキングルールは9種類あり、複数該当する場合の優先順位が決まっている。

カスタムルーチン(UDF) > ランダムハッシュ > SHA-256ハッシュ > メールマスク
  > 最後の4文字 > 最初の4文字 > 日付年マスク > デフォルト値 > 無効化(null)
ルール 挙動 JOIN 可否
SHA-256 ハッシュ 決定論的にハッシュ化 ⭕️ 可能
ランダムハッシュ クエリごとに結果が変わる 同一クエリ内のみ
メールマスク abc123@gmail.com → XXXXX@gmail.com ❌
最初 / 最後の4文字 4文字だけ残して XXXXX（4文字以下なら SHA-256） ❌
日付年マスク 2030-07-17 → 2030-01-01 ❌
デフォルト値 型ごとの既定値（"", 0, 1970-01-01 00:00:00 UTC） ❌
無効化 null に置換（型情報も隠す） ❌

必要な IAM ロール:

  • マスク済みデータの閲覧: BigQuery Masked Reader（roles/bigquerydatapolicy.maskedReader）
  • データポリシー管理: BigQuery Data Policy Admin
  • ポリシータグ管理: Data Catalog Policy Tag Admin

Tip

決定論的 SHA-256 マスキングは便利だが「マスキングしたから仮名加工情報」ではない。
マスキングは見せ方の制御で、元テーブルには生データが残っている。法的カテゴリを変えたいなら、加工結果を別テーブルとして物理的に作る必要がある。

dbt での持ち方 

models:
  - name: pseudo_events
    config:
      tags: ["pseudonymized"]
    meta:
      privacy_class: pseudonymized      # personal | pseudonymized | anonymized | statistical
      legal_basis: "法41条（個人情報である仮名加工情報）"
      mapping_table: "prj-pii-vault.mapping.user_pseudonym"
    columns:
      - name: pseudo_id
        meta:
          pii: false
          note: "sha256(user_id + salt)。対応表は prj-pii-vault に隔離"
      - name: age
        meta:
          pii: false
          note: "規則31条では特異な記述の削除は不要なので生値を保持"
  • privacy_class を必須メタデータにして、CI で未設定モデルを落とす
  • exposures を書いておくと「この仮名加工情報がどのダッシュボードに流れているか」＝ 目的外利用の検知に使える

よくある誤解

誤解 実際
ハッシュ化すれば個人情報ではなくなる 対応表・元データを持つ限り容易照合性あり ＝ 個人情報。法41条が適用される
仮名加工情報なら第三者提供できる ❌ 原則不可。委託・共同利用・事業承継のみ
匿名加工情報にすれば自由に使える 加工5要件 ＋ 作成時の公表・提供時の明示・識別行為禁止が付いてくる
仮名加工情報は漏えい報告義務がないから安全 報告義務は外れるが安全管理措置義務は残る。事故が許されるわけではない
集計してマートにすれば法の話は終わり n=1 セルなど対応関係が排斥されていない集計は統計情報ではない
dataset を分ければ照合性は切れる 「同一事業者内で一般的な方法で照合できるか」で判断。IAM と運用まで含めて分離する
匿名加工情報は仮名加工情報の上位互換 目的が違う。社内分析なら仮名加工情報のほうが有用性が高く加工も軽い

GDPR との対応に注意

日本 近い英語 GDPR での扱い
個人情報 Personal Information / Personal Data personal data
仮名加工情報 Pseudonymously Processed Information pseudonymised data は依然 personal data（GDPR Art.4(5), Recital 26）
匿名加工情報 Anonymously Processed Information anonymous data に近いが、GDPR の anonymisation はより厳格
統計情報 Statistical / Aggregate Data 対象外

Caution

「pseudonymised だから GDPR の対象外」は通らない。
日本法には「個人情報でない仮名加工情報」（法42条）というカテゴリが存在するが、GDPR に対応する概念はない。
クロスボーダー案件では日本法の箱と GDPR の箱を別々に判定する。
