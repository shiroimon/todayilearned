0. 借りたのは判定軸だけ

Neo4j + Ollama + LangChain で手を動かす構成の無料本。全 9 章。原稿は DevRev-JP/tech-blog に Markdown で置いてあるので、Zenn の SPA を相手にせず raw で読める。

この記事で借りたのは、本の判定軸 3 つだけ。KG そのものの入門は本を読めば済むので書かない。

借りた軸 中身
Safe Zone / Unsafe Zone 誤答コストが低い領域は LLM 単体で足りる。高い領域は構造で根拠を保証する
Unsafe Zone 判定チェックリスト 10 項目。「はい」が 0 個なら Safe、1〜2 個ならハイブリッド、3 個以上で KG + LLM
改善手法でも解けない 4 つ 権限外情報の混入 / 否定形・制約 / リアルタイム整合 / 数値・金額の計算

3 つめは「HyDE も Reranker も GraphRAG も、ベクトル検索を賢く使う方向の改善であって、ベクトル類似度という仕組みの限界そのものは動かさない」という整理から来ている。

Warning

割り引いて読んだところ。冒頭の「生成 AI パイロット案件の 95% が失敗する」は MIT NANDA の調査由来で、そこから KG の必要性までは一足飛びに繋がらない。本文中の定量値も「筆者推察」「推測」と自己申告のラベルが付いたものが多い。第 7 章の権限フィルタは著者自身が疑似実装と断っており、GraphCypherQAChain も allow_dangerous_requests=True で回っている。構成と判定軸は使えるが、数字はそのまま引用しない。

Note

本は AI Agent の成熟度を L1〜L5 で呼ぶ。自分のメモリ運用も強制力を L0〜L3 で呼んでいるが、別物。以下で L2 と書いたら後者（毎セッション自動注入される層）を指す。

1. 1ファイル1事実は、書いた後からノードとエッジだった

.claude/memory/ は「1 ファイル = 1 つの事実」で運用している。KG の語彙に置き換えると、意図せず property graph の形になっていた。

KG の語彙 .claude/memory/ での実体
ノード *.md 1 ファイル
ノードラベル frontmatter の type（feedback / project / reference / user）
エッジ 本文の [[slug]]
プロパティ pain_count recall_count last_verified promoted_to reviewed_digest
オントロジー frontmatter の規約。hooks/memory/frontmatter_guard.sh が形を守る
コミュニティ CLUSTERS.md の C1〜C4
検索インターフェース MEMORY.md（索引。description が刺されば本体が読まれる）

実測してみる。

$ ls -1 .claude/memory/*.md | wc -l
      15

$ grep -oh '\[\[[^]]*\]\]' .claude/memory/*.md | sort | uniq -c | sort -rn
   6 [[recall-count-semantics]]
   5 [[slug]]
   5 [[memory-index-hard-limits]]
   3 [[til-ai-era-writing-policy]]
   2 [[project-deploy]]
   1 [[wakatime-setup-refs]]
   1 [[til-env-preamble-convention]]
   1 [[til-ai-leverage-plan]]
   1 [[feedback-no-destructive-verification]]
   1 [[]]

ノード 15、エッジ 20 本 / 相異なる宛先 8 種。勝手にグラフになった、という話ではない。メモを書くときの規約に「関連は [[slug]] で張る」を入れてあり、まだ書いていない記憶へのリンクも許容している。エッジを張る操作をルールにしたから形が付いた。

Caution

この grep の行数をそのままエッジ数にすると間違える。[[slug]] (5) と [[]] (1) は README.md の記法説明に出てくる雛形であってエッジではない。数えるなら雛形を除いて宛先で畳む。

$ python3 -c "
import re, glob, pathlib, collections
t = collections.Counter()
for f in glob.glob('.claude/memory/*.md'):
    for m in re.findall(r'\[\[([^\]]*)\]\]', pathlib.Path(f).read_text()):
        if m.strip() not in ('', 'slug', 'their-name'): t[m] += 1
print('エッジ', sum(t.values()), '/ 宛先', len(t))
"
エッジ 20 / 宛先 8

一方 KG と決定的に違うところが 1 つある。エッジに型が無い。 [[slug]] は「関連」としか言っておらず、SUPERSEDES なのか CONTRADICTS なのか EXAMPLE_OF なのかは本文の日本語を読まないと分からない。本は最小構成として「ノードタイプ 5〜10 個・リレーションシップタイプ 10〜20 個」を勧めているので、こちらはリレーション 1 種（無型）で下限にすら届いていない。

Note

未解決リンクを壊れ扱いしない、という判断が後で効いた。memory_staleness_scan.py は [[slug]] の解決先を検証するが、未解決は findings に出さず件数だけ出す。壊れと呼ぶのは「かつて在ったものが動いた / 消えた」場合だけ。KG のデータ品質検査でいう孤立ノード検出をそのまま持ち込むと、予約として張ったリンクが全部ノイズになる。

ちなみに現時点の未解決は 0 件（8 宛先すべて実体がある）。ルールが効くのは本数が増えていく時期のほうで、今は「鳴らない状態」を維持できているだけ。

2. KG が得意とされる操作を、自分の運用に当てて採点する

本のフローチャートは「集計・否定・経路探索が必要か」で分岐する。5 つに割って、.claude/memory/ では誰がやっているかを並べた。

操作 KG での例 自分の運用での対応 担い手
経路探索 承認者を 2 ホップ辿る [[slug]] を辿って関連メモへ LLM（本文を読む）
集計 ノード数のカウント 索引の行数・文字数 memory_gc_scan.py
否定 [:PROHIBITED] エッジ 「themes/ を編集しない」「rm はしない」 L2（CLAUDE.md / rules/）
時刻依存 現在有効な条件はどれか last_verified / reviewed_digest /memory-review
競合解決 どちらが新しく正しいか superseded_by / 3 点一致で潰す 人間

採点すると、機械で解けているのは「集計」だけだった。残り 4 つは人間か LLM が本文を読んで判定している。

面白かったのは 否定。本はベクトル検索が最も落としやすい情報として否定形を挙げ、KG では [:NOT_SUPPORTED] [:PROHIBITED] のような明示的なエッジで持て、と書く。自分のメモリで否定形が主張そのものになっているもの（テーマ編集禁止・破壊的検証の禁止）は、L1 のメモに置かず L2 に上げてある。毎セッション強制注入される層まで持ち上げる＝想起の確率に賭けないという選択で、やっていることは「否定を構造で持て」と同じ結論に着いている。KG を建てずに層を上げるだけで済ませた形。

Caution

否定形は逆にスキャナを誤爆させる。memory_staleness_scan.py は本文中のパスを実在チェックするので、「.github/workflows/deploy.yml は無効化されている」のような不在を主張するメモも、実在を主張するメモと同じ顔で鳴る。「実在の主張」と「単なる言及」は機械では区別できない。allowlist で黙らせる器を作ると実際のドリフトまで一緒に飲み込むので、除外リストではなく記述のほうを変えて解くことにした。

3. 索引には 200 行 / 25,000 文字の天井がある

グラフの規模制約に相当するもの。ただしこれは運用で決めた数字ではなく、Claude Code 本体のハードコード。

The first 200 lines of MEMORY.md, or the first 25KB, whichever comes first, are loaded at the start of every conversation. Content beyond that threshold is not loaded at session start.

押さえたのは 3 点。

  1. 「かつ」ではなく「どちらか先」。行数超過と文字数超過を独立に見て、両方セーフな時だけ素通しする。エントリが長い運用では 200 行に届く前に文字数側で切られる
  2. 単位は UTF-16 文字数でバイトではない。「25KB」は 25,000 を 1024 で割った表示上の数字で、日本語なら 25,000 文字 ≒ 73KB。wc -c のバイト数で見ると余裕を過小評価して、要らない剪定を走らせる
  3. 超過分は末尾から黙って落ちる。Claude 側にはエラーが返るが、人間の画面には何も出ない

そして索引に限り、frontmatter や HTML コメントも算入される。CLAUDE.md 階層のローダはそれらを剥がしてから字数を数えるが、MEMORY.md は生テキストのまま渡っていて剥がす処理を通らない。

実測はこれで取る。

$ python3 -c "
import pathlib
t = pathlib.Path('.claude/memory/MEMORY.md').read_text().strip()
print('lines :', t.count(chr(10))+1, '/ 200')
print('chars :', len(t.encode('utf-16-le'))//2, '/ 25000')
"
lines : 18 / 200
chars : 1124 / 25000

まだ余っている。ただし実効上限は行数ではなく文字数側が先に来る計算で、平均エントリ長が 125 文字を超えた時点で名目の 200 行には永久に届かなくなる。値を焼き込まず毎回測ることにした。

Tip

枠が詰まった時の第一手は「本体を捨てる」ではなく「索引の行を縮める」。メモ本体側に実質の上限が無いので、索引から落とす文言を先に本文へ移せば情報損失が構造的にゼロになる。捨てるのは最後。

4. スキャナは 3 本あって、どれも意味を見ない

スクリプト 見るもの 判定手段 使う場面
memory_gc_scan.py 索引枠（行数・文字数） 数える /memory-gc
memory_cluster_scan.py 精読の被覆と再読対象 台帳と突合 /memory-review
memory_staleness_scan.py アンカー（パス・[[slug]]・judgment #N）の実在 実体と照合 随時

3 本とも read-only で、意味を見るものは 1 つも無い。意味 —「同じことを別の言葉で言っていないか」「射程が切れていないか」— を判定するのは本文を読んだ人間と AI だけ、と決めている。

そこに落ち着いたのは、意味の代理指標を 3 つ試して全部却下したから。

代理指標 実際に測っているもの 却下の理由
recall_count 本文を Read で開いた回数 索引の description で足りる短い良メモは永遠に 0
本文 3-gram / 語彙 Jaccard 文字列の重なり 意味を見ない。上位ペアは「同じ話題の別の事実」
経過時間 / last_verified 最後に裏取りした日 事実の重みは経過時間に比例しない

2 つめの却下理由が、本の言う「ベクトル検索は意味のパターンマッチングであって関係性の推論ではない」とそのまま同じ話だった。表層の重なりで「これは重複です」と言えたためしがない。 上位に来るのは決まって「同じ話題の別の事実」で、潰すと片方の主張が消える。

なので /memory-review では、潰す条件を 3 点すべての一致（主張の中核 / 一次根拠 / 引くべき場面）に絞った。3 つめが欠けるペアは相互リンクだけ足して残す。エッジを増やす方向に倒す、というのがグラフっぽい着地だと思う。

陳腐化の検出も、時間軸をやめて アンカーの実在に切り替えた。「古いから落とす」ではなく「前提が壊れた時に鳴らす」。本文にすでに埋まっている参照を取り出して実体と突き合わせる方式で、これは KG のデータ品質検査（リンク切れ・孤立ノード）とほぼ同じ発想に自然に着いた。

Important

鳴らなかったことは「全部健在」を意味しない。機械照合できるアンカーを持たないメモが相当数あるので、スキャナの出力末尾には必ず走査条件と限界を出させている。「無音＝健全」と読むと、そこが一番大きい盲点になる。

5. 読む機械と、書く人間を分けた

本には「読み取り専用エージェントと書き込みエージェントの分離」という節があり、Neo4j のロールを分けて読み取り側に書き込み権を与えない実装が載っている。HITL の境界も L2 と L3 の間 —「エージェントが提案し、人間が決定する」までが L2 — として引かれている。

自分の運用も、意図せず同じところに線がある。

操作 誰が
事実を書く Claude（auto-memory）／人間
枠・被覆・実在を測る スキャナ 3 本（read-only）
剪定・退避を提案する /memory-gc /memory-review
剪定・退避を確定する 人間

/memory-retrospective /memory-gc /memory-review は人間が明示的に叩いた時だけ動く。週次の nudge は出るが、それは表示するだけで起動条件ではない。しかも nudge は suppressOutput で人間の画面にしか出さず、Claude の context には入れていない。促しを読んだ AI が自分で走り出すのを構造的に塞いである。

削除も同じ線の内側。rm は使わず mv で .archive/ へ移すだけにしてある。この環境には Time Machine もローカルスナップショットも無く、未コミット変更の復旧手段が存在しないため。退避したら .archive/README.md の台帳に 1 行足す — 索引から消えたメモを辿れる唯一の手掛かりになる。

6. チェックリストは Unsafe Zone と出たが、Neo4j は入れなかった

本の 10 項目チェックリストを自分のメモリ運用に当てる。「はい」が 3 個以上なら KG + LLM のアーキテクチャが必要、という基準。

# 項目 判定 理由
1 金額・数値の正確性 いいえ メモに金額は無い
2 権限・認可の判定 いいえ 単一ユーザー・単一リポジトリ
3 法的・規制上の要件 いいえ —
4 時刻依存の重要情報 はい 射程切れ・last_verified の管理がまさにこれ
5 複数文書にまたがる推論 いいえ クラスタ精読は 2〜3 本単位
6 否定・禁止・制限の取り扱い はい 主張が否定形のメモが複数ある
7 個人・組織固有のデータ はい 全部このリポジトリ固有の事実
8 回答の根拠の説明責任 いいえ —
9 多段階の関係性の推論 いいえ 3 ホップ以上のチェーンが出たことがない
10 競合する情報の解決 はい superseded_by / 重複判定

4 個。本の基準に素直に従えば Unsafe Zone、KG を建てろという判定になる。それでも入れなかった理由は 3 つ。

1. チェックリストは誤答コストの「種類」を測るが「規模」を測らない。 ノード 15・エッジ 9 種で、grep と ls で全部見える。Neo4j を常駐させ、オントロジーを設計し、バックアップの面倒を見るコストが、解いている問題に対して明らかに過剰。本自身も「オントロジー設計は一度決めると変更コストが高い」と書いていて、まだ設計を固めたくない規模だという自覚のほうが強かった。

2. DB に載せた瞬間、想起が「問い合わせ」に戻る。 今いちばん効いている解法は §2 の「否定形は L2 に上げる」で、これはグラフ問合わせではなく毎セッション全文注入。強制力はクエリの精度ではなく、注入される層にいることから来ている。KG に載せ替えると「問い合わせないと出てこない」情報に格下げされ、想起の確率に賭ける側へ戻ってしまう。KG は L1 の中を賢くする技術で、L2 の代わりにはならない。

3. 一番効いた変更はグラフと関係なかった。 メモの実体を .claude/memory/ に置き、~/.claude/projects/.../memory からシンボリックリンクを張って、リポジトリで git 追跡させた。これでマシンを変えても記憶が消えない。ストレージの形式ではなく、置き場所の問題だった。

$ ls -ld ~/.claude/projects/-Users-takuya-hirukawa-Sandbox-TIL/memory
lrwxr-xr-x@ ... -> /Users/takuya.hirukawa/Sandbox/TIL/.claude/memory

何が来たら考え直すかは決めておく。

  • メモが 100 本規模になって [[slug]] の手張りが破綻したら
  • エッジに型が要るようになったら（SUPERSEDES と CONTRADICTS を区別しないと潰す判断ができなくなったら）
  • 記憶が複数リポジトリに散って、どこへ落とすかの判断が要るようになったら（今は単一リポジトリなので「場所」の分岐自体が無い）

どれも「本数」ではなく「手で辿れなくなったか」が閾値。今はまだ手で辿れている。
