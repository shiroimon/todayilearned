発端: AWS の「二段構え」

AWS で S3 にクロスアカウントアクセスさせるときは、許可を 2 箇所 に書く。

  • 主体側（アクセスする側のアカウント）の IAM ポリシー
  • リソース側（バケットがあるアカウント）の バケットポリシー

同一アカウントなら片方だけでよく、別アカウントになった途端に両方必須になる。さらに S3 アクセスポイントを挟むと、アクセスポイントへの許可とは別に その先のバケットへの許可 も要る。

Google Cloud で同じことをやるとどうなるか、が以下。

結論: Google Cloud は基本「リソース側だけ」

IAM の allow policy は リソースに貼るものしかない。AWS の identity-based policy に当たる「プリンシパル側に貼って、行き先を書くポリシー」が標準の仕組みとして存在しない。

なので別プロジェクト・別組織のプリンシパルに触らせたいときも、リソース側の allow policy にプリンシパルを 1 行足すだけで成立する。

# 別組織のユーザーに、このバケットだけ読ませる
$ gcloud storage buckets add-iam-policy-binding gs://BUCKET_NAME \
    --member='user:someone@other-example.com' \
    --role='roles/storage.objectViewer'

相手のプロジェクト側で対になる設定は要らない。AWS で言えば「バケットポリシーだけ書けば通る」状態。

観点 AWS (S3) Google Cloud
主体側に貼るポリシー IAM ポリシー 標準では無い（PAB は上限のみ）
リソース側に貼るポリシー バケットポリシー allow policy
同一アカウント / プロジェクト どちらか片方でよい リソース側 allow policy のみ
別アカウント / プロジェクト 両方必須 リソース側 allow policy のみ
境界になる単位 アカウント プロジェクト（境界は弱い）

Note

Google Cloud のプロジェクトは AWS アカウントほど硬い壁ではない。組織 → フォルダ → プロジェクト → リソースという階層の一段でしかなく、プリンシパルの識別子（メールアドレス）は組織を越えてそのまま書ける。だから「クロス」に特別な作法が生まれなかった、という理解をしている。

プリンシパルとロールの語彙

公式はプリンシパルを 2 つに大別する。

  • Human users … Google Account / Google group / workforce identity pool の federated identity
  • Workloads … service account / workload identity pool の federated identity

--member に書く識別子はこの型で決まる。user: group: serviceAccount: domain: principalSet://...。

ロールは 3 種類。

  • Predefined roles … Google Cloud 側が管理。基本これを使う
  • Custom roles … 自分で権限を列挙する。保守コストが高く、組織・プロジェクトあたりの個数上限もある
  • Basic roles（Owner / Editor / Viewer）… 広すぎるのでテスト用。本番非推奨

権限そのものは service.resource.verb の形（resourcemanager.projects.list）。

階層と継承

Organization → Folder → Project → Resource の順に継承する。上に付けた allow policy は配下すべてに効く。

押さえておくこと: allow policy に引き算は書けない。上位で付いたロールを下位で「ここだけ外す」ことはできない。外したいときは後述の deny policy か PAB を使う。

「ロールは付いてるのに弾かれる」ときに見る順番

allow が付いているのに 403 なら、理由は allow の外側にある。評価は allow → deny → PAB の順で、公式いわく IAM always checks relevant deny policies before checking relevant allow policies。deny は allow より先に評価され、allow を覆す。

  1. deny policy … deniedPrincipals / deniedPermissions / exceptionPrincipals / denialCondition の 4 要素。組織・フォルダ・プロジェクトにアタッチでき、配下に継承する
  2. PAB（principal access boundary）policy … プリンシパル側にバインドして「行ける先の上限」を決める。can only block or not block access—they can’t grant access。AWS の identity-based policy に構造が一番近いのはこれだが、許可はできない
  3. 組織ポリシー / ドメイン制限共有（iam.allowedPolicyMemberDomains）… 許可ドメイン外のプリンシパルは付与自体が失敗する。エラーは One or more users named in the policy do not belong to a permitted customer。自組織の Customer ID すら自動では許可されないので allowed_values に明示が必要
  4. VPC Service Controls … IAM とは別レイヤの境界
  5. Cloud Storage なら public access prevention（allUsers / allAuthenticatedUsers を封じる）
  6. 反映待ち … Changes to a principal’s access are eventually consistent

切り分けは Policy Troubleshooter に投げるのが早い。

$ gcloud beta policy-intelligence troubleshoot-policy iam RESOURCE \
    --principal-email=EMAIL \
    --permission=PERMISSION

Important

beta を付けないと PAB を見てくれない（allow / deny だけ）。PAB で落ちているケースを追うときは beta 必須。

例外: Google Cloud でも二段になるところ

「リソース側だけ」が崩れる場所がいくつかある。ここが実務でハマる。

BigQuery: 実行するプロジェクトとデータのあるプロジェクトが別

何に対する権限 どこで必要か 権限 ロール
ジョブを作る クエリを 実行 するプロジェクト bigquery.jobs.create roles/bigquery.jobUser
データを読む テーブルが ある プロジェクト bigquery.tables.getData roles/bigquery.dataViewer 以上

見た目は AWS の「両方必須」に近いが、理屈は違う。片方は ジョブという別リソース への権限で、もう片方が データ への権限。「主体側の許可」が要るわけではなく、2 つのリソースに触っているだけ。

課金プロジェクトとデータ置き場を分ける構成だと必ず踏む。

クロスプロジェクトのサービスアカウント

プロジェクト A の SA を、プロジェクト B のリソースにアタッチするのは デフォルトで禁止。SA を専用プロジェクトに集約している構成でぶつかる。

  • iam.disableCrossProjectServiceAccountUsage がデフォルトで enforce。プロジェクトレベルでしか設定できない（フォルダ・組織では不可）
  • 解除すると project lien（origin: iam.googleapis.com/cross-project-service-accounts）が自動で付き、プロジェクトが削除できなくなる。lien の削除は強く非推奨。iam.restrictCrossProjectServiceAccountLienRemoval も併せて enforce しておくのが推奨
  • SA に対して、使う側サービスの service agent へ roles/iam.serviceAccountTokenCreator を付与
  • アタッチする人には iam.serviceAccounts.actAs（roles/iam.serviceAccountUser）
$ gcloud resource-manager org-policies disable-enforce \
    iam.disableCrossProjectServiceAccountUsage \
    --project=SERVICE_ACCOUNT_PROJECT_ID

$ gcloud iam service-accounts add-iam-policy-binding \
    SA_NAME@SA_PROJECT_ID.iam.gserviceaccount.com \
    --member='serviceAccount:SERVICE_AGENT_EMAIL' \
    --role='roles/iam.serviceAccountTokenCreator'

Warning

一度有効にしたあとに戻すと、動いていたリソースが正しく動かなくなる可能性がある（公式が明記している）。本番では実質片道。

service account impersonation

  • roles/iam.serviceAccountTokenCreator（iam.serviceAccounts.getAccessToken）が必要
  • 出てくるのは short-lived credentials。有効期間は数時間以下、自動更新なし。SA キーを配るより安全
  • gcloud <command> --impersonate-service-account=SA_EMAIL で単発、設定に入れるなら impersonate-service-account プロパティ
  • コンソールでは impersonate できない（ユーザー認証情報のみ）
  • 監査ログには元のプリンシパルと SA の両方が残る

Cloud Storage: IAM と ACL は AND ではなく OR

AWS と正反対なのがここ。公式の表現は「これらのシステムは並行して機能します。ユーザーが Cloud Storage リソースにアクセスするには、いずれかのシステムが権限を付与する必要があります」。

AWS が「IAM とバケットポリシーの 両方 で許可」なのに対し、Cloud Storage は「IAM か ACL の どちらか が許可すれば通る」。しかも互いを検知できないので、意図しない公開が起きる方向に倒れる。

  • Uniform bucket-level access（推奨） … ACL を無効化して IAM だけにする。managed folders / IAM Conditions / ドメイン制限共有などが使えるのはこちらだけ
  • Fine-grained … IAM + ACL 併用。オブジェクト単位で細かく制御できるが、上の OR が効く
  • uniform に切り替えたあと 90 日以内なら fine-grained に戻せる（それを過ぎると戻せない）

IAM / ACL とは別に、署名付き URL（signed URL）で時間制限付きのアクセスを渡す手もある。

現状確認に使うもの 

# リソースに貼られている allow policy を見る
$ gcloud projects get-iam-policy PROJECT_ID
$ gcloud storage buckets get-iam-policy gs://BUCKET_NAME

# あるプリンシパルが特定リソースに特定権限を持つか（allow / deny / PAB 横断）
$ gcloud beta policy-intelligence troubleshoot-policy iam RESOURCE \
    --principal-email=EMAIL --permission=PERMISSION
