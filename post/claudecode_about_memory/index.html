Why

SSIA

セッションを切るたびに、同じ前提を最初から説明し直していないだろうか。

「このテーマディレクトリは触るな」「デプロイは CI じゃなくてローカルスクリプト」—— 一度言ったはずのことを毎回言い直しているなら、それは 記憶に落ちていない ということ。

CLAUDE.md に全部書けばいい、という発想だと今度は肥大化する。 全部を毎回読ませるのはトークンの無駄だし、指示が多いほど個々の指示は薄まる。

なので「どの粒度の情報を、どの層に置くか」を決める必要がある。

What

0. 記憶は3層ある

層 生存期間 読まれるタイミング 向いている内容
セッションコンテキスト そのセッション限り 常時 今やっている作業の文脈
CLAUDE.md 永続 毎セッション必ず全文 常に効いてほしいルール
memory/ ディレクトリ 永続 関連しそうな時だけ 個別具体の事実・事故・経緯

ポイントは3行目。memory/ はインデックスだけが常時読まれ、本体は必要になった時に引かれる。 つまり「知っておいてほしいが毎回は要らない」情報の置き場になる。

Tip

判断の目安は「このルールを外したら、どのセッションでも困るか？」。 Yes なら CLAUDE.md、「特定の作業をする時だけ困る」なら memory/。

1. CLAUDE.md の階層

上から順に読まれ、下（プロジェクト側）が具体的な指示として効く。

~/.claude/CLAUDE.md              # 全プロジェクト共通（個人設定）
<project>/CLAUDE.md              # プロジェクト固有（リポジトリにコミットする）
<project>/<subdir>/CLAUDE.md     # そのディレクトリで作業する時だけ追加で読まれる

自分の運用では、グローバル側はほぼ 「各プロジェクトの CLAUDE.md に従え」だけ にしている。

# CLAUDE.md

プロジェクト固有の指示は各プロジェクトディレクトリの `CLAUDE.md` に記載されている。
カレントディレクトリまたはその親ディレクトリに `CLAUDE.md` が存在する場合、その内容に従うこと。

グローバルに具体的なルールを書くと、関係ないプロジェクトでも毎回そのトークンを払うことになる。 「全プロジェクトで例外なく守るべきこと」以外はプロジェクト側に置く。

追記の手段は2つ。

# セッション中に思いついたルールをその場で追記
# 行頭に # を打つと、どのファイルに書くか聞かれる
# デプロイは必ず script/deploy.sh を使う

# エディタで直接開いて編集
% claude
> /memory

Warning

CLAUDE.md は肥大化する。 「一度書いたルール」は消しにくいので、四半期に一度は読み返して落とすくらいでちょうどいい。 効いていないルールが残っていると、生きているルールの相対的な重みが下がる。

2. memory/ ディレクトリ — 1ファイル1事実

プロジェクトごとに、以下の場所に記憶が溜まる。

~/.claude/projects/<プロジェクトパスをハイフン化したもの>/memory/

このブログ（/Users/xxx/Sandbox/TIL）だと、こうなる。

% ls -1 ~/.claude/projects/-Users-xxx-Sandbox-TIL/memory/
MEMORY.md                                # 索引（毎セッション読まれる）
feedback_no_destructive_verification.md
feedback_no_theme_edit.md
project_deploy.md

MEMORY.md は索引だけ。1行1件、本文は絶対に書かない。

- [テーマ編集禁止](feedback_no_theme_edit.md) — themes/github-style は直接編集NG、layouts/static でオーバーライド
- [デプロイ方式](project_deploy.md) — CI不使用、ローカルスクリプトでビルド＆`public/`コミット運用
- [破壊的検証の禁止](feedback_no_destructive_verification.md) — `git checkout`等の実演は実ツリー禁止、この環境は復旧手段ゼロ

各ファイルは frontmatter + 本文。

---
name: <short-kebab-case-slug>
description: <一行要約 — 想起すべきか判断するのに使われる>
metadata:
  type: user | feedback | project | reference
---

<事実。feedback / project は **Why:** と **How to apply:** を続ける。
関連する記憶は [[別のname]] でリンクする。>

description が効く。ここだけを見て「今の作業に関係あるか」が判断されるので、 本文の要約ではなく「どういう時に思い出してほしいか」を書く方が当たる。

type は4種類。

type 中身 例
user ユーザー自身のこと（役割・熟練度・好み） 「SQL は書けるが Go は読める程度」
feedback 仕事の進め方への指示・指摘 「テーマディレクトリは直接編集するな」
project コードや git 履歴からは読み取れない経緯・制約 「CI ビルドに移す予定はない」
reference 外部リソースへのポインタ ダッシュボード URL、チケット

3. 実際に溜まっているもの

抽象論だと粒度が分からないので、実物を出す。

feedback — テーマ編集禁止 

themes/github-style ディレクトリのファイルは決して編集しない。

**Why:** サブモジュール管理されており、直接変更すると submodule 更新時に競合・消失する。
**How to apply:** テンプレートやスタイルの変更は layouts/ や static/ に同名ファイルを作成してオーバーライドする。

Why があることで、「サブモジュールじゃない別テーマなら編集していい」という応用が効く。 理由なしのルールは、状況が変わった時に破棄も適用もできなくなる。

project — デプロイ方式 

TIL サイト（Hugo）のデプロイは **ローカルスクリプトで実行** する運用。
CI（GitHub Actions 等）でのビルドは現時点で予定なし。`public/` もリポジトリに含めてコミットしている。

**Why:** ユーザーが 2026-04-15 に明言。今のところ CI 運用に移す予定はない。

**How to apply:**
- `:fileModTime` ベースの lastmod 解決がローカルでは安全に使える前提で提案してよい。
- もし将来 CI ビルドに移行する話が出たら、`hugo.toml` の `lastmod` 順序を見直す必要があることをリマインドする。

「ユーザーが 2026-04-15 に明言」——相対日付ではなく絶対日付で書く。 「先月」は、読み返した時点では何も指していない。

feedback — 事故から生まれたルール

一番効いている記憶は、実際に壊した時に書かれたものだった。

`git checkout <dir>` / `git restore` / `rm -rf` など破壊的なコマンドの挙動を
「実演・検証」する目的で、ユーザーの実作業ツリーに対して実行してはいけない。

**Why:** あるデプロイスクリプトのバグを「実演」するため実リポジトリで同コマンドを実行し、
未コミットの編集を消失させたことがある。バックアップ機構が無く、`git add` もされていなかったため、
復旧経路が一つも存在しなかった。

**How to apply:**
- 検証前に `git status` で未コミット変更の有無を必ず確認する。差分があるなら実ツリーでの破壊的操作は禁止。
- 「元に戻せるから大丈夫」と判断する前に、この環境にバックアップ機構が無いことを前提に置く。
- 読み取り専用の検証（md5 突合など）は実ツリーで可。書き込みを伴うなら退避してから。

Caution

「同じミスを3回したらルール化する」という運用がよく紹介されるが、 1回でも取り返しがつかないもの（データ消失・本番反映・外部への送信）は 3回待たずにその場で書く。3回目は存在しないかもしれない。

4. 書かないもの（アンチパターン）

書かない 理由
ディレクトリ構成・関数の一覧 読めば分かる。しかも真っ先に陳腐化する
過去に直したバグの経緯 git log が持っている
CLAUDE.md に既にある内容 二重管理になり、片方だけ更新されて矛盾する
そのセッションだけで意味を持つこと 次のセッションではノイズ
「先週」「この前」などの相対表現 読み返した時点で意味を失う

要は、リポジトリが既に記録していることは書かない。 記憶に書く価値があるのは「コードを読んでも分からないこと」だけ。

5. 忘れさせる

記憶は増える一方だと必ず腐る。間違っていると分かった記憶は消すのが正しい運用。

> /memory                      # CLAUDE.md 側を編集
> memory/ の xxx は古いので消して

さらに、記憶そのものに「忘れる条件」を書いておく手もある。

**How to apply:**
- この制約は Terraform v1.5 系での話。v1.6 以降に上げたらこの記憶は破棄すること。

記憶が指しているファイルや関数が既に無い、という事故もよく起きる。 記憶にファイル名やフラグ名が出てきたら、鵜呑みにせず実在を確認してから使うのが前提。

6. 溜まった記憶を運ぶ

~/.claude/projects/ 配下はローカルにしか無いので、マシンを変えると消える。 記憶をリポジトリ側に持たせて共有・可搬にするツールも出てきている。
